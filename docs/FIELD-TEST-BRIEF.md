# Бриф полевой проверки duo-пайплайна (обезличенный)

> Шаблон для повторной боевой проверки инструмента на небольшом проекте. **Задание серии здесь не
> описано** — оно выдаётся оператору отдельным файлом. У брифа два адресата:
> **ОПЕРАТОР** (агент, ведёт серию: разделы 1–3, 6) и **КОНТРОЛЁР** (человек или старший агент,
> наблюдает и принимает: разделы 0, 4, 5, 7). Оператор читает и раздел 4 — чтобы знать, по чему его
> будут проверять; контролёр обязан дочитать до конца раздела 3 — там пробы без модели.
>
> Плейсхолдеры `<…>` заполняются в разделе 0. Пути — абсолютные. Файл — часть инструмента: проектных
> имён и адресов в нём нет, их держит проект (`.duo/config.json`) и таблица раздела 0.

## 0. Параметры прогона (заполняет контролёр ДО старта)

| параметр | значение |
|---|---|
| `<PROJECT_DIR>` — каталог проекта (git-репозиторий) | |
| `$DUO_HOME` — клон инструмента на этой машине | |
| файл задания (выдаётся оператору отдельно) | |
| режим / изоляция: `pair`, `duo` или `solo`; `shared` или `--worktree` (**выбирать непокрытый в бою сценарий — таблица в п. 1**) | |
| число серий в прогоне (1 или 2; при 2 — вторая на worktree, первая закончена) | |
| `gates.steps` проекта (какие шаги; пусто — `duo gates` ответит rc=2, это норма) | |
| запретные зоны (файлы/каталоги/процессы, которые серия трогать не вправе) | |
| порты и процессы, не принадлежащие задаче (не занимать, не перезапускать) | |
| потолок бюджета прогона, $ (ориентиры — п. 4.6) | |
| автономность оператора: **A** — `--continue` (запуск кода) только после «ОК» контролёра; **B** — оператор продолжает сам, контролёр смотрит постфактум | |
| куда писать отчёт о находках | |

## 1. Что проверяем и почему

Первый боевой прогон (16.11.2026: серии `pair/shared` и `duo/worktree` на стороннем проекте) прошёл
цикл план → код → merge без сбоев оркестратора, но вскрыл шесть дыр в инструменте. Они исправлены;
последующие прогоны — **полевая проверка исправлений плюс поиск новых дыр**. Цель контролёра — не «серия
прошла», а «каждое исправление сработало там, где раньше ломалось, и ничего нового не сломалось».

| находка | суть | правка (где описана: `docs/CHEATSHEET-CONTROL.md`, раздел «Восстановление серии…») |
|---|---|---|
| Н1 | перезапуск серии требовал `rm -rf pipeline/<task>` и терял `task.md` (`init` писал шаблон молча) | `duo reset`; `init` предупреждает о пропавшем `task.md`; `run` не стартует на шаблоне |
| Н2 | закоммиченный `pipeline/<task>/` в базе worktree-серии ловился после создания worktree и ветки | отказ `init --worktree` и `run` ДО создания чего-либо |
| Н3 | `worktree_base` переживал удаление worktree и ветки — пересоздание шло на устаревшей базе | свежая база; откат создания при сбое provisioning |
| Н4 | `duo gates` для незакоммиченной серии молча проверял бейзлайн `HEAD` | ВНИМАНИЕ + `--dirty`; `--extra` принимает каталоги |
| Н5 | заготовленный `task.md` другой серии блокировал `commit-by-plan --yes` | чужие артефакты — отдельная неблокирующая категория |
| Н6 | ретраи ответов-заглушек ревьюера видны только в логе | счётчики в `review_telemetry` и в `status --task` |

Второй прогон (серия `pair/worktree` на свежем Python-проекте) подтвердил Н1–Н4 в бою (Н5 и Н6 не проявились)
и дал шесть новых находок; их правки — в этой версии инструмента:

| находка | суть | правка |
|---|---|---|
| Н7 | `rc` пробы «отказ rc≠0» записан зелёным: команда была под `\| tail`, rc брался от `tail` | дефект брифа: правило в разделе 3 |
| Н8 | `--extra <каталог проекта>` по букве брифа передали абсолютным путём — отказ | абсолютный путь внутри корня проекта принимается; вне корня — отказ; формулировка пробы уточнена |
| Н9 | оператор сделал `git add -A` в дереве серии перед гейтами → `commit-by-plan --yes` отказал (чужой staging), три повтора | отказ подсказывает `git -C <дерево> reset`; правило «не `git add` до `commit-by-plan`» (гейтам индекс не нужен: `gates --dirty`) |
| Н10 | у свежего Python-проекта нет игнора `__pycache__` → `.pyc` блокировали `--yes` и ушли ревьюеру как «выход за files_touch» | `setup` дописывает игнор; `init` предупреждает, если его нет |
| Н11 | в момент решения о `--continue` нет краткой сводки «что принято» | сводка в `status --task` и перед стартом `run --continue` |
| Н12 | `--dry-run` не предсказывал отказ по чужому staging (и по пустым группам) | `--dry-run` печатает «предсказание для `--yes`: пройдёт/ОТКАЖЕТ — причины» по тем же правилам |

Третий и четвёртый прогоны (17.11.2026: две серии подряд, обе `pair/worktree` на малом Python-проекте;
57 и 59 мин, $10.25 и $8.98) прошли без остановок и `halt`: **регрессий Н1–Н12 нет, новых дефектов
оркестратора операторы не нашли** (две «красные» минуты оказались их собственными ошибками: правка файла
клона в пробе P4, не откатанная к P5, и `json.load` на смешанном выводе `status`). Ревьюеры ловили реальное:
план — невыполнимую формулу DoD в задании самого оператора, импл — два дефекта кода за две итерации REVISE.
Разбор сырых артефактов серий и повторный прогон проб добавил ещё три пункта; их правки — в этой версии:

| находка | суть | правка |
|---|---|---|
| Н13 | исполнитель положил скрипт симуляции в `pipeline/<task>/` worktree-серии; там `pipeline/<task>` — симлинк на основное дерево, и `Path(__file__).resolve()` увёл загрузку модуля в основное дерево со старым кодом (`AttributeError`, потерян ход модели) | предупреждение в промпте исполнителя worktree-серии. Заодно: блок изоляции раньше не попадал в `solo`-промпт (`run --solo --worktree`) — теперь попадает |
| Н15 | `status --task X` печатает JSON состояния и текстовые строки подряд — `json.load` падает «Extra data» | `status --task X --json` — ровно один JSON-объект |
| Н16 | `gates --extra <каталог>` при изменённом файле внутри каталога всё равно печатал «ВНИМАНИЕ: ref НЕ содержит N незакоммиченных» — предупреждение держалось после ровно той правки, которую само советует | файлы, покрытые `--extra`, в счёт не входят (shared); у worktree-серии `--extra` берёт файлы из другого дерева — там ВНИМАНИЕ остаётся |
| Н14 | не дефект: `task.md`, положенный вручную ДО `init`, сохраняется (порядок «`init` → правь» и «файл → `init`» равноправны) | описано в п. 2.4 |

**Покрытие в бою после правок Н1–Н12.** Повторять один и тот же сценарий смысла нет — он трижды зелёный:

| сценарий | проверен в бою |
|---|---|
| `pair` + `--worktree`, одна серия за раз | да, 3 прогона |
| `duo` + `--worktree` | **нет** (последний — 16.11, до правок) |
| `shared` (Н4 `--dirty`, Н9 чужой staging в живой приёмке) | **нет** (только пробы) |
| `solo` и `solo --worktree` (Н13) | **нет** |
| две параллельные worktree-серии: зоны, `claims`, `merge` по очереди | **нет** (последний — 29.10, до правок) |
| аварийные пути: `halt`, `--resume`, `reset` после настоящего отказа | **нет** (P1–P2 — только пробы) |
| Н6 (заглушки ревью), Н8 (`--extra`) | после правок ни разу не понадобились (Н8 закрывает проба P4 с абсолютным путём; Н6 — только наблюдать) |

Контролёр в разделе 0 выбирает **непокрытую** строку: `pair/worktree` повторять ради регрессии имеет смысл
не чаще раза на новую версию инструмента.

## 2. Инструкции оператору: подготовка

**Инструмент — единый источник истины.** Код оркестратора не менять и не копировать в проект; найденные
шероховатости фиксировать отчётом (раздел 6). Обязательное чтение до старта:
`$DUO_HOME/docs/CHEATSHEET-CONTROL.md` (команды, режимы, worktree, гейты, `commit-by-plan`, `merge`,
«Восстановление серии…»), `$DUO_HOME/docs/PROJECT-SETUP.md` (ключи `.duo/config.json`),
`$DUO_HOME/docs/CHEATSHEET-WATCHDOG-FAILSAFE.md` (таймер надзора).

1. **Версия инструмента.** `cd $DUO_HOME && git pull --ff-only`; затем `duo reset --help` должна
   отвечать, а `duo status --help` — содержать `--json` (нет команды/флага — инструмент старый, прогон не
   начинать). `duo selftest` — персоны и модель на месте.
2. **Проект.** `cd <PROJECT_DIR>`; нужен git и ≥1 коммит (worktree-сериям). Подключён ли проект —
   `duo projects`; нет — `duo setup`. `.duo/` и `.gitignore` закоммичены **до** первой серии (иначе
   `commit-by-plan --yes` откажет на непокрытых файлах). Рабочее дерево проекта перед стартом чистое
   либо чужой WIP известен контролёру и записан в журнал (п. 6).
3. **Секреты** (`.env`, токены, ключи) не читать вслух, не коммитить, не копировать в артефакты серии.
4. **Задание — в `task.md`.** Включить: критерии приёмки (DoD), запретные зоны из раздела 0; для
   worktree-серии — требование закончить план секцией `## files_touch` (заголовок строго без номера) и
   таблицей `## commit_plan` с непересекающимися глобами. Файл можно положить **до** `init`
   (`mkdir pipeline/<task>` + файл, либо `init --task-file F`) или править после — существующий `task.md`
   `init` не перезаписывает.
   - **DoD с числами и формулами — проверить на выполнимость самому, до старта.** Ревьюер плана умеет
     найти невыполнимое условие (в бою — формула с недостижимой границей в задании оператора): это не
     помеха, а ценность, но стоит итерации и денег. Нашёл — исправление зафиксировать в журнале.
   - **Пороги метрик фиксировать в `task.md` ДО прогона** (пре-регистрация) и не подгонять параметры под
     порог: порог не достигнут — это результат, он идёт в отчёт и решается человеком. Ревьюер принимает
     именно честный отчёт.
5. **Ловушки подготовки (регулярно всплывали):**
   - **Не коммитить `pipeline/<task>/` worktree-серии до её `merge`** — ни `task.md`, ни прочее. Если
     закоммитил — `init --worktree` откажет (это штатно, но потерянное время). Не коммитить и
     «заготовленный заранее» `task.md` следующей серии.
   - **Не `rm -rf pipeline/<task>` и не править `state.json`.** Сброс серии — только
     `duo reset --task X --dry-run`, затем `--yes`.
   - **Не `git add` в дереве серии до `commit-by-plan`** (в worktree серии тоже). Гейтам индекс не нужен:
     до коммитов — `duo gates --task X --dirty`. Чужой staging блокирует `commit-by-plan --yes`; снять —
     `git -C <дерево серии> reset` (сбрасывает только индекс). Перед `--yes` всегда `--dry-run`.
   - **Python-проект: `__pycache__/` в `.gitignore`, закоммичено ДО серии** (для worktree — до `run`: база
     берётся из HEAD). `duo setup` это делает; `init` предупреждает, если игнора нет.
   - Файл оператора `operator_log.md` держать **внутри** `pipeline/<task>/` (артефакт своей серии не
     попадает в «файлы вне групп»); любой иной файл прямо под `pipeline/` блокирует `commit-by-plan --yes`.
   - **Скрипты (симуляции, замеры) из `pipeline/<task>/` в worktree-серии.** Там `pipeline/<task>` — симлинк
     на основное дерево: `Path(__file__).resolve()`/`realpath` уведёт в основное дерево со **старым** кодом
     (Н13). Корень брать от cwd (запуск из корня worktree) или `Path(__file__).absolute()`. Исполнитель
     получает это предупреждение в промпте; оператор, пишущий скрипты сам, — помнить.
   - **Вывод инструмента для скриптов — только `duo status --task X --json`** (один JSON-объект). Обычный
     `status --task X` — JSON и текст подряд, `json.load` на нём падает. Либо читать `state.json` напрямую (только чтение).

## 3. Предполётные пробы (без модели, ≈5 минут, $0)

**Код возврата проверять сразу и без пайпа:** `cmd; echo rc=$?` (в `cmd | tail` rc берётся от `tail` и покажет
«0» при честном отказе; если пайп нужен — `${PIPESTATUS[0]}`).

Выполняет оператор **в одноразовом клоне проекта** — реальный проект и реестр надзора не затрагиваются
(`setup` в клоне НЕ запускать). Контролёр читает вывод каждой пробы и сверяет с «ожидается». Любой
красный результат → **серию не начинать**, сообщить контролёру, приложить вывод.

```bash
PROBE=$(mktemp -d); C=$PROBE/p
git clone -q --no-hardlinks <PROJECT_DIR> $C
# все команды ниже: duo --repo $C …   (глобальный флаг — ДО подкоманды)
```

| # | проба | команды | ожидается | красный флаг |
|---|---|---|---|---|
| P1 | `run` не стартует на шаблоне (Н1) | `duo --repo $C init --task fieldprobe1` → `duo --repo $C run --task fieldprobe1 --fg` | отказ, rc≠0, текст «остался шаблоном «Опиши задачу здесь.»»; в `$C` нет `.worktrees/` | запуск пошёл (потрачены деньги) или тишина |
| P2 | `reset` бережёт задание (Н1) | `printf '# Задача\nпроба на несколько строк\n' > $C/pipeline/fieldprobe1/task.md; sha256sum` того файла → `reset --task fieldprobe1 --dry-run` → `reset --task fieldprobe1 --yes` → `sha256sum` снова → `init --task fieldprobe1` → `sha256sum` | хеш `task.md` один и тот же трижды; в `pipeline/fieldprobe1/` появился `_reset_<метка>/` со `state.json`; печатается «task.md: СОХРАНЯЕТСЯ» | хеш изменился; `state.json` не уехал; `init` затёр задание |
| P3 | отказ до создания worktree (Н2) | `mkdir -p $C/pipeline/fieldprobe2 && printf '# Задача: x\nтест\n' > $C/pipeline/fieldprobe2/task.md && git -C $C add -f pipeline/fieldprobe2/task.md && git -C $C commit -qm probe` → `duo --repo $C init --task fieldprobe2 --mode pair --worktree`; затем `ls $C/.worktrees; git -C $C branch --list 'duo/*'; ls $C/pipeline/fieldprobe2` | отказ «закоммичен в базу ветки», rc≠0; `.worktrees/` нет; веток `duo/*` нет; `state.json` не создан. Тот же `init` БЕЗ `--worktree` — проходит (если в конфиге проекта не задано `git.isolation=worktree`) | `init` прошёл; появились worktree/ветка/state |
| P4 | `gates` не молчит про бейзлайн (Н4) — **только если заданы `gates.steps`** | `duo --repo $C init --task fieldprobe4`; дописать строку в отслеживаемый файл **внутри каталога `<D>`** под git (напр. `lib/…`); `duo --repo $C gates --task fieldprobe4 --dry-run`; то же с `--dirty`; то же с `--extra <D>` **дважды: относительным путём и абсолютным `$C/<D>`** (Н8, Н16 в бою не проверялись). **В конце P4 откатить правку: `git -C $C checkout -- .`** — иначе в P5 она станет «файлом вне групп» и даст ложный отказ (так оператор получил красное в бою) | без флагов: «ВНИМАНИЕ: ref=HEAD НЕ содержит 1 незакоммиченных… БЕЙЗЛАЙН»; с `--dirty` — строка `--dirty:` без ВНИМАНИЯ; с `--extra <D>` (обе формы) — rc=0 и **без** ВНИМАНИЯ (файл покрыт, Н16); после отката `git -C $C status --short` показывает только `?? pipeline/` (артефакты проб), изменённых файлов проекта нет | молчание при грязном дереве; `--extra <D>` отвергнут (любая форма); ВНИМАНИЕ остаётся при покрытом файле (регрессия Н16); правка не откачена к P5 |
| P5 | чужие артефакты не блокируют (Н5, в бою ещё не проявлялась) и `--dry-run` предсказывает исход (Н12) | команды — в блоке «P5/P6» ниже; последняя: `duo --repo $C commit-by-plan --task fieldprobeA --version 1 --dry-run; echo rc=$?` | строка «артефакты ДРУГИХ серий (не блокируют…)» с файлами `fieldprobeB` (и прочих `fieldprobe*`, заведённых прежними пробами в этом же клоне); в «вне групп» их нет; «предсказание для `--yes`: пройдёт»; rc=0 | `fieldprobeB` в uncovered; предсказание «ОТКАЖЕТ» |
| P6 | чужой staging виден до `--yes` (Н9/Н12) | продолжение P5 (блок ниже): `git add` файла → тот же `--dry-run` → `git reset -q` → `--dry-run` снова | с индексом: «чужой staging», подсказка `git -C … reset`, «предсказание для `--yes`: ОТКАЖЕТ — индекс уже содержит…», rc=1; после `reset` — снова «пройдёт», rc=0 | dry-run зелёный при застейдженном файле; нет подсказки |

```bash
# P5/P6 — выполнять в клоне $C из предыдущего блока
duo --repo $C init --task fieldprobeA
duo --repo $C init --task fieldprobeB            # «чужая» серия: у неё есть task.md и state.json
printf '## commit_plan\n\n| группа | файлы (glob) | сообщение | rationale |\n|---|---|---|---|\n| G1 | probe_src.txt | feat: проба | п.1 |\n' \
  > $C/pipeline/fieldprobeA/impl_report_v1.md
echo x > $C/probe_src.txt
duo --repo $C commit-by-plan --task fieldprobeA --version 1 --dry-run; echo rc=$?          # P5: «пройдёт», rc=0
git -C $C add probe_src.txt
duo --repo $C commit-by-plan --task fieldprobeA --version 1 --dry-run; echo rc=$?          # P6: «ОТКАЖЕТ», rc=1
git -C $C reset -q
duo --repo $C commit-by-plan --task fieldprobeA --version 1 --dry-run; echo rc=$?          # снова «пройдёт», rc=0
```

P7 (только если в проекте нет игнора `__pycache__`; иначе пропустить): в клоне `duo --repo $C setup --yes --no-register` →
в `$C/.gitignore` блок «Python-мусор прогонов» с `__pycache__/`; повторный `setup` дубликатов не даёт.

P8 — машинный вывод состояния (Н15):

```bash
duo --repo $C init --task fieldprobe8
duo --repo $C status --task fieldprobe8 --json > $PROBE/s.json; echo rc=$?
python3 -c 'import json,sys; d=json.load(open(sys.argv[1])); print(d["phase"], d["process"]["kind"], d["budget"])' $PROBE/s.json
```

Ожидается: rc=0 и строка вида `plan idle {...}` — весь `s.json` разбирается как один JSON-объект. Красный флаг:
`JSONDecodeError` («Extra data» — в stdout попал текст) или нет ключей `phase`/`process`/`budget`.

```bash
rm -rf "$PROBE"      # только этот mktemp-каталог; в каталоге проекта rm -rf запрещён
```

Фиксируется: дата, версия инструмента (`git -C $DUO_HOME log -1 --oneline`), вывод P1–P8 — в раздел
«предполёт» журнала оператора (п. 6).

**Когда пробы можно не повторять.** Пробы привязаны к версии инструмента и конфигу проекта. Если
`git -C $DUO_HOME rev-parse HEAD` совпадает с версией последнего **полностью зелёного** предполёта на этой
машине (запись в журнале предыдущей серии) и `.duo/config.json` проекта не менялся — оператор вправе их
пропустить, записав в журнал версию, ссылку на тот предполёт и само решение (так сделано в бою, второй серией
за день). Любое изменение версии или конфига — пробы заново; контролёр может потребовать их всегда.

## 4. Контролёр: что отслеживать в ходе пайплайна

### 4.1 Принципы наблюдения

- **Источники истины — не пересказ оператора:** `pipeline/<task>/orchestrator.log` (события),
  `duo status --task X` / `--all` (процесс, бюджет, режим, зона, транспорт ревью), `duo wait --task X`
  (`WAIT-RESULT: …`), `state.json` (**только чтение**), `git` в обоих деревьях (основном и worktree).
- **Числа оператора перепроверять самому:** «тесты зелёные», «ruff чист», «N строк» — независимым
  прогоном в чистой копии (`duo gates`) или собственной командой. Отчёт исполнителя — гипотеза.
- **Каждое наблюдение — с отметкой времени и ссылкой** на строку лога/файл. Это сырьё для отчёта (раздел 6).
- Контролёр сам **не чинит** серию и инструмент: вмешательство — через оператора и штатные команды.

### 4.2 Чек-лист по этапам

**Старт (`init` → `run`)**

| что смотреть | ожидается | красный флаг |
|---|---|---|
| режим и изоляция | лог: `серия: режим <m>, изоляция <i>`; `state.json` содержит `mode`, `isolation` ровно как в разделе 0 | расхождение; пин не записан |
| создание worktree (Н3) | лог: `создан worktree … (ветка duo/<task>, база <sha10>)`; `<sha10>` = `git rev-parse --short=10 HEAD` основного дерева **на момент создания** | база старше HEAD; строка `БАЗА: пин worktree_base … устарел` при заведомо свежем старте (значит остался пин прошлой попытки — выяснить, откуда) |
| проверка Н2 до старта | `git ls-tree -r --name-only HEAD -- pipeline/<task>` пусто | не пусто, а `init --worktree` прошёл — регрессия Н2 |
| дерево человека | `git branch --show-current` в `<PROJECT_DIR>` не изменилась; `git status --short` — только артефакты `pipeline/` и заведомо известный WIP | ветка переключена; изменён чужой файл |
| шаблон задания (Н1) | если оператор запустил `run` с нетронутым шаблоном — отказ | серия стартовала на шаблоне |

**План**

| что смотреть | ожидается | красный флаг |
|---|---|---|
| ревью | `duo`: `дуо R1 (вслепую, параллельно)` → R2/R3 → председатель; `pair`: один проверяющий; вердикты `ACCEPT`/`REVISE` в `revNNN_plan.md` | вердикт без цитат плана; ревью «ни о чём» |
| содержание `plan_vN.md` | каждый пункт DoD из `task.md` имеет место в плане — **сверять построчно с `task.md`**, а не по пересказу; для worktree — `## files_touch` (без номера), `## commit_plan` с непересекающимися глобами | пункт DoD потерян; `files_touch` шире задачи или пуст |
| зона (worktree) | `ЗОНА: plan_vN.md заявляет N путей записи: …` — N и пути соответствуют задаче | `зона записи не заявлена` для worktree-серии |
| эрраты | `ЭРРАТЫ: блок revNNN_plan.md дописан в plan_vN.md` один раз; повтор — `уже в … без изменений` | двойное дописывание; `блока «Эрраты» нет` при том, что в ревью они есть |
| ошибка в самом задании | ревью плана вправе найти дефект **в `task.md`** (невыполнимая формула DoD, противоречие пунктов) — это эррата, а не придирка; оператор записывает её в журнал, а исправленное условие — в отчёт | эррата против DoD проигнорирована; оператор молча правит `task.md` под план (хеш изменён — см. «Приёмка») |
| заглушки ревьюеров (Н6) | `ВНИМАНИЕ: ответ … заглушка … ретрай с уточнением` — ретрай прошёл; `duo status --task X` печатает `транспорт ревью (деградации…)` | >2 заглушек на фазу; ретрай тоже заглушка (`abstain`); в `review_telemetry` нет ключей `stub_retries`/`transport_retries` (значит инструмент старый) |
| пауза | после ACCEPT плана — `phase=impl_pending`, оркестратор ждёт | авто-продолжение без команды |

**Пауза `impl_pending`** — точка решения контролёра. `duo status --task X` печатает строку «принято: план vN
принят ревью revNNN; эрраты: K п.; зона записи: M путей (…); потрачено $…» — сверить с собственным чтением
`plan_vN.md`: K = число пунктов блока «Эрраты», зона = `## files_touch`; расхождение — находка. `run --continue`
повторяет сводку перед запуском (`запуск имплементации: …`). Автономность **A**: контролёр читает `plan_vN.md` +
эрраты и даёт «ОК» на `run --task X --continue`. Автономность **B**: оператор продолжает сам, но в
журнале фиксирует, что проверил.

**Имплементация**

| что смотреть | ожидается | красный флаг |
|---|---|---|
| запуск | `IMPL: исполнитель имплементирует план (отчёт vN)`; `ЗОНА: серия занимает N путей записи` | зона не занята |
| подтяжка базы (worktree) | `БАЗА: worktree подтянут к HEAD основного дерева …` либо понятная причина «не подтягиваю» | `БАЗА: fast-forward не удался … имплементация на прежней базе` (фиксировать, чем вызвано) |
| выход из зоны | отсутствует | `ЗОНА: изменены файлы вне заявленной files_touch: …` — открыть дифф, выяснить; `ЗОНА: … ПЕРЕСЕКАЕТСЯ с работающей серией` |
| дерево человека (worktree) | `git -C <PROJECT_DIR> status --short` — только артефакты `pipeline/` | любой иной файл — утечка записи мимо worktree |
| запретные зоны | не изменены (`git diff --stat` в дереве серии против базы; для запретных процессов/портов — не затронуты) | изменены / перезапущены |
| живость | `orchestrator_bg.log` растёт; `duo status` показывает `running` | молчание >10 мин при живом lock; ложный `dead` от надзора |
| ревью кода | `IMPL ревью #N (revNNN): impl_report_vN + diff`; ревьюеры **цитируют хунки** из `diff_impl_vN.patch` | ревью без единой цитаты диффа (признак пустого ревью) |
| итерации | ACCEPT с 1–3 итераций. **REVISE с конкретикой (файл:строка, воспроизводимый сценарий, сверка с диффом) — норма и ценность, не сбой**: в бою две итерации REVISE поймали два реальных дефекта (мёртвая ветка в главном сценарии; тихое отклонение от пина плана) | REVISE на косметике или без цитат; упёрлись в лимит; `halt kind=…` (см. п. 4.5) |
| скрипты исполнителя в `pipeline/<task>/` (worktree; Н13) | исполнитель берёт корень проекта от cwd/`absolute()`; в его промпте (`transcripts/*_executor_*.md`) есть строка «симлинк на артефакты серии» | `AttributeError`/«старый код» в скрипте из каталога артефактов (грузит основное дерево); строки в промпте нет (инструмент старый) |

**Приёмка серии**

| что смотреть | ожидается | красный флаг |
|---|---|---|
| итог | `phase=done`; `impl_report_vN.md` с двумя цифрами тестов — ambient и в чистой копии | только ambient; цифры без вывода команд |
| независимая проверка | контролёр сам гонит линтер/тесты (по `gates.steps` либо вручную) и сравнивает с отчётом | расхождение с отчётом исполнителя |
| секреты | `rg` по артефактам серии и диффу на шаблоны токенов/ключей, **значения не печатать** | совпадение — немедленный инцидент |
| `task.md` | не изменён исполнителем (сравнить с исходным хешем) | изменён |

### 4.4 Красные флаги — остановить серию и разобрать

Исполнитель правит запретное; изменено дерево человека вне `pipeline/`; ветка человека переключена;
`state.json` правили руками; `rm -rf` в `pipeline/` или в каталоге проекта; секрет в артефакте; серия
«закончилась» без `phase=done`; бюджет >2× ориентира без объяснимой причины; зелёный результат только
в ambient-окружении; оператор правит код инструмента вместо отчёта.

### 4.5 Остановки и вмешательство

`phase=needs_human` + `halt kind=…` (`limit`, `budget`, `transport`, `crash`, `artifact_missing`,
`errata`) — таблица действий в `CHEATSHEET-CONTROL.md`, раздел «Остановки». Допустимо: `set-verdict`,
`rework`, `run --resume [--add-budget USD] [--add-iterations N]`. Недопустимо: правка `state.json`,
`kill` без плана (см. ниже). Каждую остановку контролёр фиксирует: вид, причина, кто и чем разрешил.

**Ловушка таймера надзора.** Если на машине включён `duo-supervise.timer`, намеренно убитая серия
через ~5 минут признаётся «мёртвой» и **автовозобновляется** за счёт бюджета (только `transport`/`crash`,
потолок 3 за 6 ч). Для паузы — снять автовозобновление (см. `CHEATSHEET-WATCHDOG-FAILSAFE.md`). Надзор
при здоровых сериях должен молчать: ложный `dead` при живом процессе — находка.

### 4.6 Ориентиры по времени и деньгам (для калибровки «нормально/ненормально»)

| режим | типичная задача | время | стоимость | источник |
|---|---|---|---|---|
| `pair/shared` | ~30 строк кода + 16 тестов | ≈ 50 мин | ≈ $5 | бой 29.10 |
| `pair/worktree` | аудит без правки кода (отчёт) | ≈ 30 мин | ≈ $7 | прогон 2 |
| `pair/worktree` | 1–3 файла, ~400–450 строк диффа (код + тесты + доки), 1–3 итерации импла | 57–59 мин | $9–10 | прогоны 3–4 |
| `duo/worktree` | многофайловая, десятки файлов | порядка 2–5 ч | ≈ $20–30 | оценка, в бою не мерялось |

Из прогонов 3–4 для разбивки: план ≈ 14–18 мин (исполнитель 4–9 + ревью 8–10) и $1.9–2.4; имплементация
≈ 30–36 мин при 1–3 итерациях; одно ревью — $1.0–1.7 (на ревью уходит ≈ 30–50% стоимости серии, остальное —
исполнитель). Разовые добавки (симуляции, замеры по заданию) поднимают время и стоимость — это не сбой.
Выше ×2 от стоимости своей строки — вопрос к контролёру (лишние итерации, холостые ревью, ретраи).

## 5. После серии: порядок приёмки (контролёр)

1. `commit-by-plan --task X --dry-run` — read-only; ждать строку «предсказание для `--yes`: пройдёт». Только
   затем `--yes` (all-or-nothing). Смотреть: чужие серии не блокируют (Н5); группы соответствуют плану;
   симлинки worktree и артефакты в коммиты не попали. Перед этим в дереве серии ничего не застейджено (Н9).
2. `duo gates --task X` (после коммитов ветка/`HEAD` уже содержат код; для shared повторить с `--dirty`
   не нужно). Цифры сверить с отчётом исполнителя.
3. Worktree-серия: `duo merge --task X --dry-run` (предсказание) → `duo merge --task X --yes`; в логе
   `MERGE: duo/X → <ветка> … зона записи отпущена`; worktree снят, ветка осталась.
4. Пост-проверки: `git log --stat` — сообщения групп осмысленны; дифф ⊆ `files_touch`; запретные зоны
   нетронуты; `duo status --all` — серия `done`, зона отпущена, процессов нет; в основном дереве нет мусора.
5. Артефакты серии коммитит человек **после** `merge`. `archive` — не сейчас (карантин 14 дней).

## 6. Журнал оператора и отчёт о находках

**Журнал** — `pipeline/<task>/operator_log.md` (внутри каталога серии): время · что сделал · команда ·
вывод/ссылка. Разделы: предполёт (раздел 3) → старт → план → пауза → код → приёмка. Каждая остановка,
ретрай, отказ инструмента и любое «странно» — строкой с временем (контролёр сверяет с `orchestrator.log`).

**Отчёт о находках** (после ПОСЛЕДНЕГО `commit-by-plan` — иначе файл под `pipeline/` вне групп заблокирует
`--yes`; либо вне `pipeline/`): путь — из раздела 0. Формат записи, как в предыдущем отчёте:

```
## Н<N> (существенная|важная|мелкая|наблюдение). Название
### Условия возникновения   — минимальные шаги/состояние, при которых воспроизводится
### Инцидент (время, серия) — строки лога/вывода дословно, ссылки на файлы
### Наблюдение              — что именно не так (механизм), чего ждал
### Предложение             — минимальная правка и её цена; что НЕ предлагаю и почему
```

В начале отчёта: версия инструмента (коммит), режимы серий, стоимость и время, статус **каждого** из Н1–Н13,
Н15, Н16 (Н14 — справочно): «сработало как задумано» / «регрессия» / «не проявилось — не проверено». Каждое
«сработало» — с доказательством (строка лога, фрагмент вывода, хеш), не просто «ОК». Затем новые находки.
**Если новых находок нет — так и написать («новых находок инструмента: 0»), не изобретать.** Отдельным
списком — **ошибки оператора** (не откатил правку клона, разобрал не тот вывод): это не дефекты инструмента,
но каждая — кандидат в бриф; к каждой приписать, что бы её предотвратило. Отдельно — «что сработало» (для
калибровки). Traceback и контекст оркестраторных ошибок приложить; **код инструмента не править и
`state.json` не трогать**.

## 7. Критерий успеха прогона (решает контролёр)

- Пробы P1–P8 зелёные (либо пропущены по правилу «версия и конфиг не менялись» — с записью в журнале);
  версия инструмента зафиксирована.
- Сценарий серии выбран из непокрытых в бою (п. 1) либо контролёр записал, зачем повторён покрытый.
- Серия(и) прошли план → код → приёмку → `commit-by-plan` → `gates` → (worktree) `merge`; `phase=done`.
- По каждому из Н1–Н13, Н15, Н16 есть явный статус с доказательством (или честное «не проявилось»); регрессий нет.
- Красных флагов (п. 4.4) не было, либо каждый разобран и записан.
- Отчёт о находках сдан в оговорённом формате; дерево человека не тронуто; запретные зоны целы.
