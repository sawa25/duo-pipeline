# Бриф полевой проверки duo-пайплайна (обезличенный)

> Шаблон для повторной боевой проверки инструмента на небольшом проекте. **Задание серии здесь не
> описано** — оно выдаётся оператору отдельным файлом. У брифа два адресата:
> **ОПЕРАТОР** (агент, ведёт серию: разделы 1–3, 6) и **КОНТРОЛЁР** (человек или старший агент,
> наблюдает и принимает: разделы 0, 4, 5, 7). Оператор читает и раздел 4 — чтобы знать, по чему его
> будут проверять; контролёр обязан дочитать до конца раздела 3 — там пробы без модели.
>
> Плейсхолдеры `<…>` заполняются в разделе 0. Пути — абсолютные. Файл — часть инструмента: проектных
> имён и адресов в нём нет, их держит проект (`.duo/config.json`) и таблица раздела 0.

## 0. Параметры прогона (заполняет контролёр ДО старта)

| параметр | значение |
|---|---|
| `<PROJECT_DIR>` — каталог проекта (git-репозиторий) | |
| `$DUO_HOME` — клон инструмента на этой машине | |
| файл задания (выдаётся оператору отдельно) | |
| режим / изоляция: `pair` или `duo`; `shared` или `--worktree` | |
| число серий в прогоне (1 или 2; при 2 — вторая на worktree, первая закончена) | |
| `gates.steps` проекта (какие шаги; пусто — `duo gates` ответит rc=2, это норма) | |
| запретные зоны (файлы/каталоги/процессы, которые серия трогать не вправе) | |
| порты и процессы, не принадлежащие задаче (не занимать, не перезапускать) | |
| потолок бюджета прогона, $ (ориентиры — п. 4.6) | |
| автономность оператора: **A** — `--continue` (запуск кода) только после «ОК» контролёра; **B** — оператор продолжает сам, контролёр смотрит постфактум | |
| куда писать отчёт о находках | |

## 1. Что проверяем и почему

Предыдущий боевой прогон (16.11.2026: серии `pair/shared` и `duo/worktree` на стороннем проекте) прошёл
цикл план → код → merge без сбоев оркестратора, но вскрыл шесть дыр в инструменте. Они исправлены; этот
прогон — **полевая проверка исправлений плюс поиск новых дыр**. Цель контролёра — не «серия прошла», а
«каждое исправление сработало там, где раньше ломалось, и ничего нового не сломалось».

| находка | суть | правка (где описана: `docs/CHEATSHEET-CONTROL.md`, раздел «Восстановление серии…») |
|---|---|---|
| Н1 | перезапуск серии требовал `rm -rf pipeline/<task>` и терял `task.md` (`init` писал шаблон молча) | `duo reset`; `init` предупреждает о пропавшем `task.md`; `run` не стартует на шаблоне |
| Н2 | закоммиченный `pipeline/<task>/` в базе worktree-серии ловился после создания worktree и ветки | отказ `init --worktree` и `run` ДО создания чего-либо |
| Н3 | `worktree_base` переживал удаление worktree и ветки — пересоздание шло на устаревшей базе | свежая база; откат создания при сбое provisioning |
| Н4 | `duo gates` для незакоммиченной серии молча проверял бейзлайн `HEAD` | ВНИМАНИЕ + `--dirty`; `--extra` принимает каталоги |
| Н5 | заготовленный `task.md` другой серии блокировал `commit-by-plan --yes` | чужие артефакты — отдельная неблокирующая категория |
| Н6 | ретраи ответов-заглушек ревьюера видны только в логе | счётчики в `review_telemetry` и в `status --task` |

## 2. Инструкции оператору: подготовка

**Инструмент — единый источник истины.** Код оркестратора не менять и не копировать в проект; найденные
шероховатости фиксировать отчётом (раздел 6). Обязательное чтение до старта:
`$DUO_HOME/docs/CHEATSHEET-CONTROL.md` (команды, режимы, worktree, гейты, `commit-by-plan`, `merge`,
«Восстановление серии…»), `$DUO_HOME/docs/PROJECT-SETUP.md` (ключи `.duo/config.json`),
`$DUO_HOME/docs/CHEATSHEET-WATCHDOG-FAILSAFE.md` (таймер надзора).

1. **Версия инструмента.** `cd $DUO_HOME && git pull --ff-only`; затем `duo reset --help` должна
   отвечать (нет команды — инструмент старый, прогон не начинать). `duo selftest` — персоны и модель на месте.
2. **Проект.** `cd <PROJECT_DIR>`; нужен git и ≥1 коммит (worktree-сериям). Подключён ли проект —
   `duo projects`; нет — `duo setup`. `.duo/` и `.gitignore` закоммичены **до** первой серии (иначе
   `commit-by-plan --yes` откажет на непокрытых файлах). Рабочее дерево проекта перед стартом чистое
   либо чужой WIP известен контролёру и записан в журнал (п. 6).
3. **Секреты** (`.env`, токены, ключи) не читать вслух, не коммитить, не копировать в артефакты серии.
4. **Задание — в `task.md`.** Включить: критерии приёмки (DoD), запретные зоны из раздела 0; для
   worktree-серии — требование закончить план секцией `## files_touch` (заголовок строго без номера) и
   таблицей `## commit_plan` с непересекающимися глобами.
5. **Ловушки подготовки (регулярно всплывали):**
   - **Не коммитить `pipeline/<task>/` worktree-серии до её `merge`** — ни `task.md`, ни прочее. Если
     закоммитил — `init --worktree` откажет (это штатно, но потерянное время). Не коммитить и
     «заготовленный заранее» `task.md` следующей серии.
   - **Не `rm -rf pipeline/<task>` и не править `state.json`.** Сброс серии — только
     `duo reset --task X --dry-run`, затем `--yes`.
   - Файл оператора `operator_log.md` держать **внутри** `pipeline/<task>/` (артефакт своей серии не
     попадает в «файлы вне групп»); любой иной файл прямо под `pipeline/` блокирует `commit-by-plan --yes`.

## 3. Предполётные пробы (без модели, ≈5 минут, $0)

Выполняет оператор **в одноразовом клоне проекта** — реальный проект и реестр надзора не затрагиваются
(`setup` в клоне НЕ запускать). Контролёр читает вывод каждой пробы и сверяет с «ожидается». Любой
красный результат → **серию не начинать**, сообщить контролёру, приложить вывод.

```bash
PROBE=$(mktemp -d); C=$PROBE/p
git clone -q --no-hardlinks <PROJECT_DIR> $C
# все команды ниже: duo --repo $C …   (глобальный флаг — ДО подкоманды)
```

| # | проба | команды | ожидается | красный флаг |
|---|---|---|---|---|
| P1 | `run` не стартует на шаблоне (Н1) | `duo --repo $C init --task fieldprobe1` → `duo --repo $C run --task fieldprobe1 --fg` | отказ, rc≠0, текст «остался шаблоном «Опиши задачу здесь.»»; в `$C` нет `.worktrees/` | запуск пошёл (потрачены деньги) или тишина |
| P2 | `reset` бережёт задание (Н1) | `printf '# Задача\nпроба на несколько строк\n' > $C/pipeline/fieldprobe1/task.md; sha256sum` того файла → `reset --task fieldprobe1 --dry-run` → `reset --task fieldprobe1 --yes` → `sha256sum` снова → `init --task fieldprobe1` → `sha256sum` | хеш `task.md` один и тот же трижды; в `pipeline/fieldprobe1/` появился `_reset_<метка>/` со `state.json`; печатается «task.md: СОХРАНЯЕТСЯ» | хеш изменился; `state.json` не уехал; `init` затёр задание |
| P3 | отказ до создания worktree (Н2) | `mkdir -p $C/pipeline/fieldprobe2 && printf '# Задача: x\nтест\n' > $C/pipeline/fieldprobe2/task.md && git -C $C add -f pipeline/fieldprobe2/task.md && git -C $C commit -qm probe` → `duo --repo $C init --task fieldprobe2 --mode pair --worktree`; затем `ls $C/.worktrees; git -C $C branch --list 'duo/*'; ls $C/pipeline/fieldprobe2` | отказ «закоммичен в базу ветки», rc≠0; `.worktrees/` нет; веток `duo/*` нет; `state.json` не создан. Тот же `init` БЕЗ `--worktree` — проходит (если в конфиге проекта не задано `git.isolation=worktree`) | `init` прошёл; появились worktree/ветка/state |
| P4 | `gates` не молчит про бейзлайн (Н4) — **только если заданы `gates.steps`** | `duo --repo $C init --task fieldprobe4`; дописать строку в любой отслеживаемый файл кода; `duo --repo $C gates --task fieldprobe4 --dry-run`; то же с `--dirty`; то же с `--extra <каталог проекта>` | первый вывод содержит «ВНИМАНИЕ: ref=HEAD НЕ содержит 1 незакоммиченных… БЕЙЗЛАЙН»; с `--dirty` — строка `--dirty:` без ВНИМАНИЯ; `--extra` с каталогом принят | молчание при грязном дереве; `--extra каталог` отвергнут |

```bash
rm -rf "$PROBE"      # только этот mktemp-каталог; в каталоге проекта rm -rf запрещён
```

Фиксируется: дата, версия инструмента (`git -C $DUO_HOME log -1 --oneline`), вывод P1–P4 — в раздел
«предполёт» журнала оператора (п. 6).

## 4. Контролёр: что отслеживать в ходе пайплайна

### 4.1 Принципы наблюдения

- **Источники истины — не пересказ оператора:** `pipeline/<task>/orchestrator.log` (события),
  `duo status --task X` / `--all` (процесс, бюджет, режим, зона, транспорт ревью), `duo wait --task X`
  (`WAIT-RESULT: …`), `state.json` (**только чтение**), `git` в обоих деревьях (основном и worktree).
- **Числа оператора перепроверять самому:** «тесты зелёные», «ruff чист», «N строк» — независимым
  прогоном в чистой копии (`duo gates`) или собственной командой. Отчёт исполнителя — гипотеза.
- **Каждое наблюдение — с отметкой времени и ссылкой** на строку лога/файл. Это сырьё для отчёта (раздел 6).
- Контролёр сам **не чинит** серию и инструмент: вмешательство — через оператора и штатные команды.

### 4.2 Чек-лист по этапам

**Старт (`init` → `run`)**

| что смотреть | ожидается | красный флаг |
|---|---|---|
| режим и изоляция | лог: `серия: режим <m>, изоляция <i>`; `state.json` содержит `mode`, `isolation` ровно как в разделе 0 | расхождение; пин не записан |
| создание worktree (Н3) | лог: `создан worktree … (ветка duo/<task>, база <sha10>)`; `<sha10>` = `git rev-parse --short=10 HEAD` основного дерева **на момент создания** | база старше HEAD; строка `БАЗА: пин worktree_base … устарел` при заведомо свежем старте (значит остался пин прошлой попытки — выяснить, откуда) |
| проверка Н2 до старта | `git ls-tree -r --name-only HEAD -- pipeline/<task>` пусто | не пусто, а `init --worktree` прошёл — регрессия Н2 |
| дерево человека | `git branch --show-current` в `<PROJECT_DIR>` не изменилась; `git status --short` — только артефакты `pipeline/` и заведомо известный WIP | ветка переключена; изменён чужой файл |
| шаблон задания (Н1) | если оператор запустил `run` с нетронутым шаблоном — отказ | серия стартовала на шаблоне |

**План**

| что смотреть | ожидается | красный флаг |
|---|---|---|
| ревью | `duo`: `дуо R1 (вслепую, параллельно)` → R2/R3 → председатель; `pair`: один проверяющий; вердикты `ACCEPT`/`REVISE` в `revNNN_plan.md` | вердикт без цитат плана; ревью «ни о чём» |
| содержание `plan_vN.md` | каждый пункт DoD из `task.md` имеет место в плане — **сверять построчно с `task.md`**, а не по пересказу; для worktree — `## files_touch` (без номера), `## commit_plan` с непересекающимися глобами | пункт DoD потерян; `files_touch` шире задачи или пуст |
| зона (worktree) | `ЗОНА: plan_vN.md заявляет N путей записи: …` — N и пути соответствуют задаче | `зона записи не заявлена` для worktree-серии |
| эрраты | `ЭРРАТЫ: блок revNNN_plan.md дописан в plan_vN.md` один раз; повтор — `уже в … без изменений` | двойное дописывание; `блока «Эрраты» нет` при том, что в ревью они есть |
| заглушки ревьюеров (Н6) | `ВНИМАНИЕ: ответ … заглушка … ретрай с уточнением` — ретрай прошёл; `duo status --task X` печатает `транспорт ревью (деградации…)` | >2 заглушек на фазу; ретрай тоже заглушка (`abstain`); в `review_telemetry` нет ключей `stub_retries`/`transport_retries` (значит инструмент старый) |
| пауза | после ACCEPT плана — `phase=impl_pending`, оркестратор ждёт | авто-продолжение без команды |

**Пауза `impl_pending`** — точка решения контролёра. Автономность **A**: контролёр читает `plan_vN.md` +
эрраты и даёт «ОК» на `run --task X --continue`. Автономность **B**: оператор продолжает сам, но в
журнале фиксирует, что проверил.

**Имплементация**

| что смотреть | ожидается | красный флаг |
|---|---|---|
| запуск | `IMPL: исполнитель имплементирует план (отчёт vN)`; `ЗОНА: серия занимает N путей записи` | зона не занята |
| подтяжка базы (worktree) | `БАЗА: worktree подтянут к HEAD основного дерева …` либо понятная причина «не подтягиваю» | `БАЗА: fast-forward не удался … имплементация на прежней базе` (фиксировать, чем вызвано) |
| выход из зоны | отсутствует | `ЗОНА: изменены файлы вне заявленной files_touch: …` — открыть дифф, выяснить; `ЗОНА: … ПЕРЕСЕКАЕТСЯ с работающей серией` |
| дерево человека (worktree) | `git -C <PROJECT_DIR> status --short` — только артефакты `pipeline/` | любой иной файл — утечка записи мимо worktree |
| запретные зоны | не изменены (`git diff --stat` в дереве серии против базы; для запретных процессов/портов — не затронуты) | изменены / перезапущены |
| живость | `orchestrator_bg.log` растёт; `duo status` показывает `running` | молчание >10 мин при живом lock; ложный `dead` от надзора |
| ревью кода | `IMPL ревью #N (revNNN): impl_report_vN + diff`; ревьюеры **цитируют хунки** из `diff_impl_vN.patch` | ревью без единой цитаты диффа (признак пустого ревью) |
| итерации | ACCEPT с 1–3 итераций | упёрлись в лимит; `halt kind=…` (см. п. 4.5) |

**Приёмка серии**

| что смотреть | ожидается | красный флаг |
|---|---|---|
| итог | `phase=done`; `impl_report_vN.md` с двумя цифрами тестов — ambient и в чистой копии | только ambient; цифры без вывода команд |
| независимая проверка | контролёр сам гонит линтер/тесты (по `gates.steps` либо вручную) и сравнивает с отчётом | расхождение с отчётом исполнителя |
| секреты | `rg` по артефактам серии и диффу на шаблоны токенов/ключей, **значения не печатать** | совпадение — немедленный инцидент |
| `task.md` | не изменён исполнителем (сравнить с исходным хешем) | изменён |

### 4.3 Проверка каждого исправления в бою

| находка | где проявится | как проверить | красный флаг (регрессия) |
|---|---|---|---|
| **Н3** свежая база | старт worktree-серии, особенно повторный после сбоя | п. «создание worktree» выше; `state.json.worktree_base` = HEAD на момент создания | пин старше HEAD при отсутствии ветки |
| **Н2** предотвращение каскада | если оператор по привычке закоммитил `task.md` worktree-серии | `init --worktree` обязан отказать до создания; `ls .worktrees`, `git branch --list 'duo/*'` пусты | worktree/ветка созданы, а отказ пришёл позже |
| **Н1** reset и шаблон | любой перезапуск серии | только `duo reset` (в журнале оператора и истории команд нет `rm -rf pipeline/…`); хеш `task.md` до/после совпадает; есть `_reset_<метка>/`; `init` на пропавший `task.md` — ВНИМАНИЕ | `rm -rf`; `task.md` заменён шаблоном; `reset` снёс наработки без `--force` |
| **Н4** достоверность гейтов | после ACCEPT импла, **до** коммита, оператор зовёт `duo gates` (shared-серия) | вывод содержит ВНИМАНИЕ «проверит БЕЙЗЛАЙН» → оператор обязан взять `--dirty` (или сначала `commit-by-plan`); итог без `⚠`; в `logs/gates_*/summary.txt` нет `WARN` | зелёный `gates` с ВНИМАНИЕМ принят как доказательство; предупреждения нет при грязном дереве |
| **Н5** чужие артефакты | если в `pipeline/` лежит заготовка другой серии | `commit-by-plan --yes` не отказывает из-за неё, печатает «артефакты ДРУГИХ серий (не блокируют…)» | отказ «uncovered» из-за чужого каталога; оператор коммитит чужой `task.md` ради разблокировки |
| **Н6** транспорт ревью | любая серия | `duo status --task X` — строка `транспорт ревью…`, если были заглушки/повторы; в `review_telemetry` у каждой записи есть `stub_retries`, `transport_retries` | заглушка в логе, но в телеметрии нули/нет ключей |

### 4.4 Красные флаги — остановить серию и разобрать

Исполнитель правит запретное; изменено дерево человека вне `pipeline/`; ветка человека переключена;
`state.json` правили руками; `rm -rf` в `pipeline/` или в каталоге проекта; секрет в артефакте; серия
«закончилась» без `phase=done`; бюджет >2× ориентира без объяснимой причины; зелёный результат только
в ambient-окружении; оператор правит код инструмента вместо отчёта.

### 4.5 Остановки и вмешательство

`phase=needs_human` + `halt kind=…` (`limit`, `budget`, `transport`, `crash`, `artifact_missing`,
`errata`) — таблица действий в `CHEATSHEET-CONTROL.md`, раздел «Остановки». Допустимо: `set-verdict`,
`rework`, `run --resume [--add-budget USD] [--add-iterations N]`. Недопустимо: правка `state.json`,
`kill` без плана (см. ниже). Каждую остановку контролёр фиксирует: вид, причина, кто и чем разрешил.

**Ловушка таймера надзора.** Если на машине включён `duo-supervise.timer`, намеренно убитая серия
через ~5 минут признаётся «мёртвой» и **автовозобновляется** за счёт бюджета (только `transport`/`crash`,
потолок 3 за 6 ч). Для паузы — снять автовозобновление (см. `CHEATSHEET-WATCHDOG-FAILSAFE.md`). Надзор
при здоровых сериях должен молчать: ложный `dead` при живом процессе — находка.

### 4.6 Ориентиры по времени и деньгам (для калибровки «нормально/ненормально»)

| режим | типичная задача | время | стоимость |
|---|---|---|---|
| `pair/shared` | 1–3 файла, ~30–200 строк | 50–90 мин | ≈ $5–6 |
| `duo/worktree` | многофайловая, десятки файлов | порядка 2–5 ч (оценка) | ≈ $20–30 |

Нижняя граница — нормальная; выше ×2 — вопрос к контролёру (лишние итерации, холостые ревью, ретраи).

## 5. После серии: порядок приёмки (контролёр)

1. `commit-by-plan --task X --dry-run`, затем `--yes` (all-or-nothing). Смотреть: чужие серии не
   блокируют (Н5); группы соответствуют плану; симлинки worktree и артефакты в коммиты не попали.
2. `duo gates --task X` (после коммитов ветка/`HEAD` уже содержат код; для shared повторить с `--dirty`
   не нужно). Цифры сверить с отчётом исполнителя.
3. Worktree-серия: `duo merge --task X --dry-run` (предсказание) → `duo merge --task X --yes`; в логе
   `MERGE: duo/X → <ветка> … зона записи отпущена`; worktree снят, ветка осталась.
4. Пост-проверки: `git log --stat` — сообщения групп осмысленны; дифф ⊆ `files_touch`; запретные зоны
   нетронуты; `duo status --all` — серия `done`, зона отпущена, процессов нет; в основном дереве нет мусора.
5. Артефакты серии коммитит человек **после** `merge`. `archive` — не сейчас (карантин 14 дней).

## 6. Журнал оператора и отчёт о находках

**Журнал** — `pipeline/<task>/operator_log.md` (внутри каталога серии): время · что сделал · команда ·
вывод/ссылка. Разделы: предполёт (раздел 3) → старт → план → пауза → код → приёмка. Каждая остановка,
ретрай, отказ инструмента и любое «странно» — строкой с временем (контролёр сверяет с `orchestrator.log`).

**Отчёт о находках** (после ПОСЛЕДНЕГО `commit-by-plan` — иначе файл под `pipeline/` вне групп заблокирует
`--yes`; либо вне `pipeline/`): путь — из раздела 0. Формат записи, как в предыдущем отчёте:

```
## Н<N> (существенная|важная|мелкая). Название
### Условия возникновения   — минимальные шаги/состояние, при которых воспроизводится
### Инцидент (время, серия) — строки лога/вывода дословно, ссылки на файлы
### Наблюдение              — что именно не так (механизм), чего ждал
### Предложение             — минимальная правка и её цена; что НЕ предлагаю и почему
```

В начале отчёта: версия инструмента (коммит), режимы серий, стоимость и время, статус **каждого** из Н1–Н6
(«сработало как задумано» / «регрессия» / «не проявилось — не проверено»), затем новые находки. Отдельно —
«что сработало» (для калибровки). Traceback и контекст оркестраторных ошибок приложить; **код инструмента
не править и `state.json` не трогать**.

## 7. Критерий успеха прогона (решает контролёр)

- Пробы P1–P4 зелёные; версия инструмента зафиксирована.
- Серия(и) прошли план → код → приёмку → `commit-by-plan` → `gates` → (worktree) `merge`; `phase=done`.
- По каждому из Н1–Н6 есть явный статус с доказательством (или честное «не проявилось»); регрессий нет.
- Красных флагов (п. 4.4) не было, либо каждый разобран и записан.
- Отчёт о находках сдан в оговорённом формате; дерево человека не тронуто; запретные зоны целы.
