# Подключение любого git-проекта к duo-пайплайну (duoportable)

Инструмент живёт в СВОЁМ репозитории (`$DUO_HOME` — каталог клона); проект,
который им управляется, хранит у себя только свои данные: артефакты серий
`pipeline/<task>/` и тонкие переопределения `.duo/config.json`. Ниже — как
подключить проект и какие ключи проектного конфига существуют (серия
`duoportable`, R1–R10). Рабочие команды серий — `docs/CHEATSHEET-CONTROL.md`.

`duo` в командах — лаунчер `bin/duo` этого репозитория. Ставится один раз на машину:
`bash $DUO_HOME/install.sh` (симлинк `~/.local/bin/duo`, скилл для Cursor и Claude Code;
`--personas` — персоны ревьюеров, `--systemd` — таймер надзора); развёрнуто —
`python $DUO_HOME/duo_pipeline.py <команда>`. Интерпретатор лаунчер берёт сам:
`$DUO_PYTHON` → env311 → python3.12/3.11 (нужен ≥ 3.11); настройка под конкретную машину —
раздел «Несколько машин» ниже.

## Быстрое подключение: `duo setup`

```bash
cd /путь/к/проекту
duo setup                # в каталоге проекта
```

Что делает (все шаги идемпотентны, повторный запуск печатает «УЖЕ» и выходит rc=0):

1. каталог вне git → `git init` по подтверждению (`--yes` — неинтерактивно;
   без tty и без `--yes` — отказ с подсказкой); после init при нулевом числе
   коммитов — предупреждение (worktree-сериям нужен хотя бы один коммит);
2. каркас `.duo/config.json` — ТОЛЬКО если файла нет (существующий конфиг
   проекта не перезаписывается никогда);
3. `.gitignore`: рантайм серий под маркером
   `# duo-pipeline: рантайм серий (duo setup)` — записи `pipeline/*/.lock` и
   `/.worktrees/` (дубликатов не делает);
4. регистрация проекта в реестре надзора
   `${XDG_CONFIG_HOME:-~/.config}/duo-pipeline/projects.json`
   (`--no-register` — пропустить).

**После `setup` закоммить `.duo/` и `.gitignore` ДО первой серии.** Незакоммиченные файлы
`commit-by-plan --yes` считает «не покрытыми» и отказывает (all-or-nothing).
**Но не коммить `pipeline/<task>/` (в т.ч. заранее написанный `task.md`) для worktree-серии до её `merge`:**
в worktree этот каталог обязан быть симлинком на основное дерево, и закоммиченный в базе — `init --worktree`/`run`
отказывают. Артефакты ДРУГИХ серий `commit-by-plan` блокирующими не считает.

Дальше: `duo init --task <имя>` → `duo run --task <имя>` (как обычно,
см. шпаргалку). Управление реестром: `duo projects [--add PATH] [--remove PATH]
[--prune]` — таблица «проект / каталог на месте / .duo / активных серий».

## Корень проекта (R1): как оркестратор находит репозиторий

Приоритет (каждый следующий используется, если предыдущих нет):

1. флаг `--repo PATH` (глобальный, ДО подкоманды: `duo --repo <путь> run --task X`);
2. переменная окружения `DUO_REPO`;
3. legacy-ключ `repo` в конфиг-слое `--config` (совместимость со старым
   `config.json`, где корень был запиннен);
4. автодетект от текущего каталога: `git rev-parse --git-common-dir` — работает
   из любого подкаталога проекта и из linked worktree (возвращает ОСНОВНОЕ дерево).

Нет корня ни одним способом: обычные команды отказываются с подсказкой
(`--repo PATH` / `DUO_REPO` / `duo setup`), а не трейсбеком. `projects`, `setup`
работают и без корня. `supervise` без явного указания (флаг/DUO_REPO/legacy)
идёт в режим реестра — автодетект НЕ применяется (таймер не должен надзирать за
тем репо, в каталоге которого случайно живёт). Detached-перезапуск всегда
передаёт ребёнку явный `--repo` — серия не зависит от cwd родителя.

## Конфиг (R2): три слоя

    DEFAULTS (в duo_pipeline.py)  <  config.json инструмента (--config)  <  <проект>/.duo/config.json

- слои сливаются `deep_merge`'ом: словари — по ключам, **списки замещаются
  целиком** (чтобы проектный `gates.steps` не склеивался с чужим);
- пути в `claude_config_dir`, `council_agents_dir`, `gates.python`, `gates.stubs`
  раскрывают `~` и `$VAR`;
- собранный cfg содержит `_project_config_path` — путь проектного слоя, если
  файл существует (иначе `null`);
- старый конфиг с ключом `repo` продолжает работать (см. R1, п. 3).

## Ключи проектного слоя (`.duo/config.json`)

| ключ | зачем |
|---|---|
| `executor_env_hint` | строка в промпт исполнителя: окружение проекта (интерпретатор, `conda run …`, стенд) |
| `executor_worktree_note` | приписка в worktree-блок промпта: сервисы/ресурсы, которые нельзя перезапускать (R7) |
| `executor_long_run_markers` | свои слова-маркеры (имена хостов/стендов проекта): задание, где они есть, получает правила длинных прогонов (в дополнение к встроенным `ssh`/`стенд`/`AMD`/`nohup`) |
| `executor_deny` | список правил `--disallowedTools` claude CLI для исполнителя (`Bash(adb:*)`, `Read(./.env)`, `Edit(./config/**)`): технический запрет, действует и в bypass-режиме; не защита от обхода через интерпретатор — раздел «Серии на живом оборудовании» |
| `audit` | правила `duo audit`: `deny_bash`/`deny_read`/`deny_script` (списки regex) и `write_zones` (каталоги записи, `{task}` подставляется; токен `@plan` — ещё и зона из `## files_touch` принятого плана: файлы, каталоги, globs; у solo/серии без такой секции не раскрывается, о чём `audit` говорит прямо) — проверка постфактум по журналу сессии исполнителя |
| `resources` | имена общих ресурсов проекта (`adb:phone-1`, `gpu:0`): серия держит машинный замок на время `run`, вторая получает отказ с именем держателя (`run --wait-resources SEC` — ждать) |
| `acceptance.steps` | шаги живой приёмки `duo accept` (формат как у `gates.steps`: `argv` без shell, `name`, `timeout_sec`, `inconclusive_rc`, `inconclusive_match` — regex по выводу шага при rc ≠ 0 → INCONCLUSIVE; лучше разный rc в самой команде): идут в дереве серии под замками `resources`; вердикт PASS/FAIL/INCONCLUSIVE → `state.json`, `phase` не меняется |
| `gates.python` | интерпретатор гейтов. **Обычно не задавать** (null → `sys.executable` оркестратора): путь непереносим между машинами — «Несколько машин» |
| `gates.stubs` | каталог пакетов-заглушек для pytest-шагов (null/`""` → заглушек нет; относительный путь — от корня проекта, напр. `.duo/gate_stubs`) |
| `gates.cpus` | ядра для `taskset` (подставляется в `{cpus}`). null → `$DUO_GATES_CPUS`, иначе ВСЕ доступные процессу ядра |
| `gates.steps` | шаги гейтов поставки — см. ниже (R3) |
| `git.isolation` | `shared` \| `worktree` — умолчание изоляции новых серий |
| `git.worktrees_dir` | каталог worktree-серий (обычно `.worktrees`) |
| `git.worktree_links` | имена корневых каталогов, которые provisioning симлинкает в свежий worktree (R4; `.env` не линкуется никогда) |
| `guard.never_revert` | tracked-пути, которые ревьюер НЕ откатывает при «ловушке отката» (правки хозяина; R5) |
| `archive.guard_exempt_files` | файлы, ссылки на которые НЕ блокируют `archive` (дополняют builtin-набор; R6) |
| `archive.guard_skip_dirs` | каталоги, внутрь которых охрана `archive` не заходит (дополняют builtin-набор) |
| `archive.merge_target_refs` | ветки, в которые должна быть слита серия для архивации (дополняют builtin `HEAD`, `main`) |
| `supervisor`, `notify`, `limits`, `timeouts`, `duo`, `pair`, `review`, `parallel`, `solo` | те же секции, что в config.json инструмента (см. `_comment`-поля там) |

### Гейты поставки (R3): `gates.steps`

Шаг — dict с ключами: `name` (имя = имя лог-файла), `argv` (список строки
команды), `pp` (нужен ли `PYTHONPATH=<заглушки>:<копия>` — как у pytest-шагов),
`timeout` (сек), `summary` (`last_line` — последняя строка вывода дословно;
`contracts` — строки контрактов lint-imports). Плейсхолдеры в `argv`:
`{py}` — полный путь интерпретатора, `{pybin}` — его каталог, `{cpus}` —
`gates.cpus`. Прогон — в чистой копии (`git archive REF` + файлы серии):
`duo gates --task X [--ref REF] [--only ruff,unit] [--extra файлы|каталоги] [--dirty] [--dry-run]`.
Для серии с незакоммиченным кодом без `--dirty`/`--extra` проверяется бейзлайн `HEAD` — `gates` об этом
предупреждает (ВНИМАНИЕ + `WARN` в `summary.txt`); `--dirty` накладывает правки дерева серии.
Пустой `gates.steps` → rc=2 с подсказкой (проект без гейтов — нормальная
ситуация). Полный набор аргументов — `duo gates --help`.

**Гейты — локальное зеркало CI проекта**, а не отдельная система: `gates.steps` должны
повторять команды CI проекта (напр. таргеты `make lint` / `make unit` / `make integration`),
и правятся они в том же коммите, что и CI. Кто потребитель каждого из трёх контуров (CI
проекта, гейты серии, CI самого инструмента) и что покрывает каждый — раздел «CI и гейты»
в `docs/CHEATSHEET-CONTROL.md`.

### Пример: проектный слой Python-проекта

Так может выглядеть `<проект>/.duo/config.json` проекта с CI из трёх таргетов
(lint = ruff + mypy + import-linter, unit, integration). Ключи, зависящие от машины
(интерпретатор, ядра), здесь намеренно НЕ заданы — см. «Несколько машин». Пиннинг формата —
`tests/unit/test_duo_gates.py`, `test_duo_portable.py`:

```json
{
  "executor_env_hint": "Интерпретатор — активное окружение проекта; юнит-тесты: python -m pytest tests/unit (без своего -q, если он уже в addopts pyproject)",
  "executor_worktree_note": "Сервис на :8080 не перезапускай.",
  "executor_long_run_markers": ["build-host"],
  "gates": {
    "stubs": ".duo/gate_stubs",
    "steps": [
      {"name": "ruff",  "pp": false, "timeout": 900,
       "argv": ["{pybin}/ruff", "check", "."], "summary": "last_line"},
      {"name": "mypy",  "pp": false, "timeout": 900,
       "argv": ["{pybin}/mypy"], "summary": "last_line"},
      {"name": "li",    "pp": false, "timeout": 900,
       "argv": ["{pybin}/lint-imports"], "summary": "contracts"},
      {"name": "unit",  "pp": true, "timeout": 7200,
       "argv": ["env", "-u", "DATA_DIR", "-u", "LOG_DIR", "taskset", "-c", "{cpus}",
                "nice", "-n", "10", "{py}", "-m", "pytest", "tests/unit", "tests/arch"],
       "summary": "last_line"},
      {"name": "integ", "pp": true, "timeout": 7200,
       "argv": ["env", "-u", "DATA_DIR", "-u", "LOG_DIR", "taskset", "-c", "{cpus}",
                "nice", "-n", "10", "{py}", "-m", "pytest", "-m", "integration and not gpu"],
       "summary": "last_line"}
    ]
  },
  "git": {"worktree_links": ["data", "models", "node_modules"]},
  "archive": {
    "guard_skip_dirs": ["data", "models", "myproj.egg-info"],
    "guard_exempt_files": ["doc/TODO.md"],
    "merge_target_refs": ["develop"]
  }
}
```

Пояснения. Списки шагов замещают целиком — проектный набор не смешивается с чужим.
`archive.*` дополняют builtin-наборы инструмента: тяжёлые каталоги не сканируются, файлы-
указатели вроде `doc/TODO.md` не блокируют удаление серии; те же значения должен держать
охранный тест проекта (в проекте-потребителе стоит завести тест, что конфиг и охранный тест
не разошлись; литералы builtin закреплены в `tests/unit/test_duo_archive.py` инструмента).
`guard.never_revert` задавайте, если в дереве проекта лежат правки, которые ревьюер не
должен откатывать (напр. генерируемые данные). Шаги `{py}`/`{pybin}` — интерпретатор, которым
запущен оркестратор; `ruff`/`mypy`/`lint-imports` должны стоять в том же окружении.

## Несколько машин (стендов): что переносимо, а что настраивается на месте

Проектный `.duo/config.json` лежит в git проекта и едет на ВСЕ машины, поэтому в нём нет
ничего машинного: ни абсолютных путей интерпретатора, ни имён хостов, ни числа ядер.
Всё машинное — в необязательном файле `${XDG_CONFIG_HOME:-~/.config}/duo-pipeline/env`
(формат `VAR=значение`, вне git). Его читает лаунчер `bin/duo`, поэтому он действует
одинаково в интерактивной оболочке, в НЕинтерактивном ssh (`ssh host duo …`), в systemd-юните
и в cron. Пример для машины с miniconda и 32 ядрами:

```
DUO_PYTHON=/home/user/miniconda3/envs/work/bin/python
DUO_GATES_CPUS=0-23
```

| что | где задаётся | поведение по умолчанию |
|---|---|---|
| интерпретатор оркестратора и гейтов (`{py}`, `{pybin}`) | `DUO_PYTHON` в env-файле | автопоиск лаунчера: `env311` в anaconda/miniconda → `python3.12/3.11/python3` (≥ 3.11). Выбранный интерпретатор лаунчер ЭКСПОРТИРУЕТ как `DUO_PYTHON`: его видят исполнитель/ревьюеры и шаги гейтов, поэтому `executor_env_hint` может ссылаться на `$DUO_PYTHON`, а не на путь машины |
| ядра для `taskset` (`{cpus}`) | `DUO_GATES_CPUS` в env-файле (или `gates.cpus`, если одинаково на всех машинах) | все ядра, доступные процессу |
| `claude` в `PATH` | лаунчер сам добавляет `~/.local/bin` | как есть |
| профиль модели, каталог персон | `claude_config_dir`, `council_agents_dir` (в config.json инструмента; `~`/`$VAR` раскрываются) | `~/.claude-glm`, `~/.claude/agents` |

Почему так (типовые вопросы).

- **Нельзя ли оставить `gates.python` в проектном конфиге?** Лучше нет: путь интерпретатора на
  одной машине (`~/anaconda3/…`) не существует на другой (`~/miniconda3/…`). Если ключ всё же
  задан и такого файла нет, `duo gates` откажет ДО запуска шагов внятным сообщением (а не
  `rc=127` в логе шага). Без ключа `{py}` = интерпретатор, запустивший оркестратор — выбор
  лаунчера/`DUO_PYTHON`. Нужен именно другой интерпретатор для гейтов — `gates.python` с
  переменной окружения (`"$GATES_PY"`), заданной в env-файле каждой машины.
- **Заглушки зависимостей (`gates.stubs`).** Инструмент своих заглушек НЕ поставляет: набор
  зависит от проекта. Заглушка — пакет, чей `__init__.py` бросает `ImportError`; каталог
  ставится первым в `PYTHONPATH` pytest-шагов и воспроизводит CI-раннер без тяжёлых пакетов
  (код, «оптимистично» импортирующий `torch`/`onnxruntime`, идёт по запасной ветке, как в CI).
  Положите их в проект (`.duo/gate_stubs/<пакет>/__init__.py`) и укажите `"stubs": ".duo/gate_stubs"`.
  Нет проблемы «тяжёлых» пакетов — ключ не нужен.
- **Подсказка исполнителю (`executor_env_hint`).** Это просто текст в промпте. Не пишите в неё
  абсолютные пути машины и свой `-q` к pytest, если `-q` уже в `addopts` проекта (второй `-q` —
  `-qq`, итоговая строка `N passed` пропадает, и отчёт остаётся без хвоста гейта).
- **Окружение гейтов на новой машине** (чек-лист): `duo` в PATH (`install.sh`), `claude` и профиль
  модели, персоны (`install.sh --personas`), `ruff`/`mypy`/`lint-imports` (версии как на основной
  машине — иначе «зелёное здесь, красное там») в окружении `DUO_PYTHON`, проект в реестре
  (`duo projects --add /путь/к/проекту`), затем `duo status --all` и `duo supervise --dry-run`.
- **Таймер надзора** — настройка машины, а не проекта: у каждого стенда свой таймер, свой реестр и своё
  состояние; он сам возобновляет «мёртвые» серии (это тратит бюджет) и без `loginctl enable-linger <user>`
  останавливается при выходе из ssh. Что делает, ловушки и чек-лист включения —
  `docs/CHEATSHEET-WATCHDOG-FAILSAFE.md`, «Таймер надзора на конкретной машине».

## Мультипроектный надзор (R8)

`supervise` без явного корня обходит ВСЕ проекты реестра
(`~/.config/duo-pipeline/projects.json`): для каждого — свой cfg
(слои `--config` + `<проект>/.duo/config.json`), состояние надзора и уведомления
— на ключах `<абс-корень>::<task>` (одноимённые серии разных проектов не
глушат алерты друг друга), заголовок уведомления `duo <проект>/<task>`,
строки лога `SUPERVISE: [<проект>] <task> …`. Пустой реестр — сообщение и rc=0.
Systemd-таймер ставится командой `bash $DUO_HOME/install.sh --systemd`
(юнит из `systemd/duo-supervise.service.in`, без `WorkingDirectory` проекта — корень больше
не нужен: supervise ходит по реестру). Установка ЗАМЕНЯЕТ ранее поставленный
`duo-supervise.*` (например, таймер прежней встроенной копии): проекты, за которыми он следил,
должны быть в реестре (`duo setup` или `duo projects --add PATH`) — иначе после замены их
серии останутся без надзора.

**Откат при замене таймера.** Прежние юниты сохраняются рядом как
`~/.config/systemd/user/duo-supervise.{service,timer}.bak-<время>` (откат: вернуть файлы,
`systemctl --user daemon-reload`). Состояние надзора лежит в `~/.local/state/duo-supervisor/state.json`
под ключами `<корень>::<task>`; записи старого формата (ключ — голое имя задачи) не
мигрируются и остаются безвредным хвостом. Первый тик по новым ключам молча «запоминает»
события старше часа: повторных уведомлений о старых `done`/`impl_pending` нет (проверяется
`duo supervise --dry-run` ДО включения таймера).

## Границы

- Код инструмента — только в репозитории duo-pipeline; проект не получает
  копий скриптов.
- `.duo/config.json` — конфиг ПРОЕКТА: оркестратор не перезаписывает его
  (каркас создаёт лишь при отсутствии).
- Реестр и состояние надзора — в XDG-каталогах пользователя, не в git-проектах.
