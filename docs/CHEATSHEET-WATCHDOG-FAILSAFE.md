# Надзор за дуо-пайплайном: штатные средства вместо внешних костылей

> Переписано 2026-10-21 (pipework3). Прежняя схема «живой bash-сторож `watchdog.sh` + одноходовка
> `watchdog_failsafe.sh` под systemd-oneshot» выведена: failsafe **не мог** перезапустить сторожа
> (systemd по завершении oneshot-сервиса убивает всю cgroup, в логе при этом стояло «перезапуск
> удался»), а сам сторож ловил смену фаз по тикам и не отличал «оркестратор умер» от «ждёт человека».

## Принцип

Источник истины о серии — **сам оркестратор**: `state.json` (phase, `halt`, `inflight`,
`state_updated_at`) + `flock` на `pipeline/<task>/.lock`. Замок держится всю жизнь процесса и снимается
ядром при ЛЮБОЙ смерти (kill -9, OOM, перезагрузка) — надёжнее `ps`/`pgrep` (тем более в песочнице, где
паттерн совпадает с командной строкой самой песочницы). Всё остальное — тонкие потребители этой правды.

Оркестратор сам гарантирует:

- любая ошибка (транспорт, бюджет, лимит итераций, «артефакт не записан», краш) — **чистая остановка**:
  `phase=needs_human` + `stop_reason` + `halt{kind,phase,resumable}` + строка `СТОП:` в `orchestrator.log`
  (+ `notify-send`, если `notify.desktop`); молчаливой смерти процесса больше нет;
- лимит итераций и бюджет проверяются **на границе итерации** (после ревью и синтеза председателя): начатая
  итерация всегда доходит до вердикта; остановка оставляет маркер доработки — `run --resume` продолжает
  ровно с неё;
- прерванный шаг исполнителя (halt или смерть процесса) возобновляется в той же сессии (`inflight`).

## Три потребителя

| слой | кто | для кого | что делает |
|---|---|---|---|
| 1 | `duo_pipeline.py wait --task X` | **агент/скрипт помощника** | блокирует до остановки/приёмки; последняя строка `WAIT-RESULT: done\|impl_pending\|halted\|dead\|idle\|timeout …`, код выхода 0/0/10/11/12/13 |
| 2 | `duo_pipeline.py supervise` (systemd-timer, раз в 2 мин) | **человек/автопилот** | `dead`/`halted` → алерт (один раз на событие) и авто-возобновление `transport`/`crash` (≤ `max_resumes` за окно); `done`/`impl_pending` → уведомление |
| 3 | `status --all` / `status --task X` | кто угодно | колонка «процесс» (running/dead/halted/idle/done), в `--task` — `lock`, возраст state, причина остановки |

### Слой 1: `wait` вместо самодельного bash-цикла + `notify_on_output`

Прежний рецепт (цикл `sleep 30` + разбор `phase` из state.json) заменяется одной командой; её вывод удобно
скармливать `notify_on_output` (паттерн `WAIT-RESULT`), а в обычном режиме — блокирующим вызовом:

```bash
cd /путь/к/проекту
duo wait --task <task> --poll 30
# фон + событийный сигнал агенту:  notify_on_output pattern "WAIT-RESULT|Error|Traceback"
```

Коды: `0` — `done` (impl принят) или `impl_pending` (план принят, пауза перед имплементацией); `10` — `halted`
(в строке `halt=<kind> resumable=<…>` и причина); `11` — `dead` (процесс умер без записи halt — `run --resume`);
`12` — `idle` (`needs_human` без машинной записи, напр. эскалация, либо серия не запускалась); `13` — `--timeout`.
Живое состояние по смене фазы/версий печатается строками `[HH:MM:SS] task: phase=… running …` (`--quiet` — без них).

Ограничение, как и у любого `notify_on_output`-цикла: он не переживает сессию агента — после рестарта сессии
`wait` запускается заново (он идемпотентен: при уже наступившем событии отвечает мгновенно).

### Слой 2: `supervise` + один systemd user-таймер

Установка (идемпотентно; заменяет и снимает старый `duo-watchdog-failsafe.timer`):

```bash
bash $DUO_HOME/install.sh --systemd
journalctl --user -u duo-supervise.service -n 5 --no-pager      # вывод последнего тика
systemctl --user list-timers 'duo-supervise*' --no-pager        # следующее срабатывание
duo supervise --dry-run   # что сделал бы надзор (ничего не меняет; без --repo — по реестру проектов)
```

Свойства:

- без состояния между тиками (дедупликация алертов и счётчики авто-возобновлений — в
  `~/.local/state/duo-supervisor/state.json`, **вне репозитория**: GitGuard вычищает посторонние untracked-файлы
  под `pipeline/`); первый тик — baseline (о прошлых `done`/`impl_pending` молчит);
- `KillMode=process` в `duo-supervise.service` — обязателен: иначе systemd убьёт вместе с oneshot-сервисом
  оркестратор, который supervise запустил detached;
- авто-возобновляются **только** `transport`/`crash` (`supervisor.auto_resume_kinds`); `limit`, `budget`,
  `errata`, `artifact_missing`, `review_empty`, `review_incomplete`, эскалации — решение человека (алерт без запуска); потолок —
  `supervisor.max_resumes` за `resume_window_sec` на задачу (защита от платного цикла);
- «мёртв» = активная фаза + `.lock` свободен + state не обновлялся ≥ `supervisor.stale_sec` (300 с) и не старше
  `dead_max_age_sec` (сутки: давние «трупы» и ни разу не запускавшиеся серии — `idle`, не тревога). Алерт о `dead`
  несёт **диагноз** (Н54): исключение из `orchestrator_bg.log` либо «записи СТОП и трейса нет — убит снаружи (OOM, kill,
  выключение)» + время последнего признака жизни + что было в полёте; цена оборванного вызова — `status`, «неучтённых…» (Н55);
- **квота провайдера** (`halt transport`, `cause=quota`, Н46/Н58): возобновляется только **после сброса** (`reset_at` +
  `quota.resume_margin_sec`), до того — действие `quota-wait`; считается отдельным потолком `supervisor.max_quota_resumes` и
  `max_resumes` не тратит; метки сброса нет — `quota-no-reset`, решает человек;
- **`halt kind=env`** (нет `claude`/`node` в PATH, Н50) надзор не возобновляет: действие `env-broken`, причина в алерте. Если
  включён `auto_resume`, а окружение службы не позволяет вызвать модель, возобновление не пробуется вовсе (`env-broken`) —
  `max_resumes` не сгорает;
- автопродолжение `impl_pending` **не делается**: запуск имплементации — решение эксперта после приёмки плана.

Без systemd: `setsid nohup duo supervise --loop --interval 60 >/dev/null 2>&1 &`
либо cron `*/2 * * * * … duo supervise`.

## Таймер надзора на конкретной машине (стенде): что он делает и как включать

Таймер `duo-supervise` — это **не фоновая служба проекта, а настройка машины**. Прочтите до включения.

**Область действия.** Таймер ставится на машину и пользователя и смотрит только на проекты из реестра
ЭТОЙ машины (`~/.config/duo-pipeline/projects.json`) и на файлы `pipeline/*/state.json` ЭТИХ клонов.
Серии, запущенные на другом стенде, он не видит: у каждого стенда свой клон проекта, свой реестр и своё
состояние надзора (`~/.local/state/duo-supervisor/state.json`). Один проект, подключённый на двух машинах,
надзирается двумя независимыми таймерами; включать таймер на каждой машине нужно отдельно.

**Что он делает без вашего участия (и во что это обходится).** Раз в 2 минуты на каждую серию:

- серия «мертва» (активная фаза, замок свободен, `state.json` не обновлялся ≥ 5 минут, но моложе суток) →
  алерт и `run --resume` в той же сессии модели, **то есть тратит деньги бюджета серии**. Так же воскресают
  серии после перезагрузки хоста, OOM, обрыва ssh и ЛЮБОГО `kill`. Потолок — 3 возобновления за 6 часов
  на задачу (`supervisor.max_resumes` / `resume_window_sec`); `limit`, `budget`, `errata`,
  `artifact_missing` и эскалации не возобновляются никогда, только алерт;
- серия завершена или план принят → уведомление (один раз на событие; о событиях старше часа молчит). Событие
  опознаётся отпечатком «фаза + потрачено + версии плана/кода», а не временем записи `state.json`: `duo accept`,
  `hold` и прочие записи state после завершения повторных уведомлений не вызывают (полевой разбор 20.11.2026:
  прежний ключ от heartbeat слал 2–4 одинаковых «ГОТОВО» на серию); доработка с новыми тратами — новое событие. Записи надзора старого формата (`<фаза>:<heartbeat>`) при
  обновлении инструмента переписываются молча — повторов по уже отмеченным сериям нет;
- запуск имплементации после принятого плана — всегда решение человека, таймер его не делает.

**Ловушка: намеренная остановка.** Серию, которую вы убили сами (`kill`, `pkill`), надзор через ~5 минут
сочтёт мёртвой и возобновит. Хотите остановить надолго — сначала `systemctl --user stop duo-supervise.timer`
(потом `start`) либо задайте `supervisor.auto_resume: false` в `.duo/config.json` проекта (тогда только
алерты). Остановки, требующие решения человека (`limit`, `budget`, …), возобновлением не затрагиваются.
Для серий на живом оборудовании (повторный запуск исполнителя снова трогает устройство) `auto_resume: false` в
проектном слое — рекомендуемое умолчание: умолчание инструмента — `true` (см. раздел «Серии на живом
оборудовании» в `CHEATSHEET-CONTROL.md`).

**Второй канал уведомлений** (Н54). Десктоп-уведомление в сессии, где никто не смотрит, — единственный сигнал: серия умерла
ночью, и человек узнал утром. Ключ `notify.command` (argv без shell, подстановки `{title}`/`{body}`, переменные
`DUO_NOTIFY_TITLE`/`DUO_NOTIFY_BODY`, `notify.command_timeout_sec`) добавляет канал — почту, мессенджер, webhook; он включён
независимо от `notify.desktop`. В строке тика итог по каждому каналу (`… \| команда: доставлено (…)` / `НЕ доставлено: …`),
`halt.notified=true` при приёме хотя бы одним каналом.

**Машина без рабочего стола (сервер, AMD-стенд).** Уведомления идут через `notify-send` (ключ
`notify.desktop`); без графической сессии и D-Bus они не доходят — сбой на работу надзора не влияет, но и
не теряется молча: итог доставки пишется в строку тика (`journalctl --user -u duo-supervise.service`):
`SUPERVISE: [проект] задача … | уведомление: <итог>`, где итог — `принято демоном уведомлений (notify-send
rc=0)` / `НЕ доставлено: <причина: нет notify-send, таймаут, rc и stderr>` / `выключено (notify.desktop=false)`
/ `уже принято демоном при остановке (оркестратор)` / `dry-run`. Единственные сигналы там — эти строки и
`duo status --all`: смотрите их сами.

**Где искать, было ли уведомление о завершении.** Не в `orchestrator.log`: оркестратор сам уведомляет только об
остановках (`СТОП`), а о `done`/`impl_pending` — надзор, и его след лишь в журнале systemd
(`journalctl --user -u duo-supervise.service | grep SUPERVISE`). Полевой разбор 20.11.2026: оператор не нашёл в
`orchestrator.log` строк `УВЕДОМЛЕНИЕ` и счёл, что уведомлений не было, — а надзор доставил их через 15 секунд
после завершения. Серия, подключённая `setup --no-register`, надзором не охватывается: её сторож — только ваш
`duo wait`. Сколько серия уже ждёт человека — `duo status --task X` (`ЖДЁТ ВАС N мин` / `ЗАВЕРШЕНА N мин назад`).

**Как читать «дошло ли уведомление».** Сама строка `notice`/`alert` в журнале доставки **не доказывает**
(полевой разбор 19.11.2026: «подтверждением» считали именно её). Доказательство — суффикс `| уведомление:
принято демоном…` (демон уведомлений принял сообщение; что человек его увидел, это не гарантирует —
режим «не беспокоить» и закрытые центры уведомлений вне власти инструмента). Для остановок оркестратор
уведомляет сам и в `state.json` ставит `halt.notified=true` **только если `notify-send` принял сообщение**;
при сбое причина — в `orchestrator.log` (`УВЕДОМЛЕНИЕ: …`), а `notified=false` — и надзор шлёт своё уведомление
сам. Ключ `notify.desktop` включён в `config.json` инструмента по умолчанию (в коде `DEFAULTS` — выключен,
для тестов); проверить эффективное значение проекта — `duo status --all` не покажет, смотрите
`.duo/config.json` и `config.json` инструмента.

### Чек-лист включения на новой машине

0. **PATH службы (Н50, обязательно перед `auto_resume`).** User-сервис systemd запускается с урезанным PATH: `claude`,
   поставленный через npm, — скрипт с `#!/usr/bin/env node`, и без каталога `node` в PATH возобновление падает
   `FileNotFoundError: 'claude'` (в поле — 4 попытки за 7 минут, `max_resumes` исчерпан). Проверка без модели:
   `env -i PATH="<PATH из Environment= unit-файла>" sh -c 'command -v claude; command -v node'` — оба пути должны
   напечататься. Нет — добавить в `duo-supervise.service` строку `Environment=PATH=<каталог claude>:<каталог node>:/usr/bin:/bin`
   (затем `systemctl --user daemon-reload`) либо задать `claude_bin` (абсолютный путь). С Н50 инструмент и сам проверяет
   окружение перед `run` и показывает причину (`env-broken`), но лучше узнать до ночи.
1. **Окружение работает.** Из каталога проекта: `duo selftest` — проверяет персоны ревьюеров, профиль
   модели и один вызов модели (≈ $0,1). Если в неинтерактивном ssh `duo` не находится в PATH —
   вызывайте `~/.local/bin/duo` полным путём. Об установке и машинных настройках — `docs/PROJECT-SETUP.md`, «Несколько машин».
2. **Проект в реестре и его конфиг на месте.** `duo projects`: колонка `.duo` должна быть «есть»
   (иначе надзор возобновляет серии с настройками инструмента по умолчанию, без проектных лимитов и
   подсказок); проект добавляется `duo setup` или `duo projects --add PATH`. Конфиг проекта приезжает с `git pull`.
3. **Репетиция.** `duo supervise --dry-run` ничего не меняет и должен ответить «все серии в порядке».
   Любое `would-resume` — серия, которую таймер возобновит в ПЕРВЫЙ же тик (на первом тике молчат только
   уведомления о завершённых, возобновления идут сразу): сначала решите судьбу этих серий.
4. **Linger (один раз на машину, нужен sudo).** `loginctl show-user $USER -p Linger` должно быть `yes`; иначе
   `sudo loginctl enable-linger $USER`. Без него user-таймер умирает при выходе из ssh и не стартует после
   перезагрузки до первого входа — а именно в этих случаях надзор и нужен. `install.sh --systemd`
   напомнит об этом, но не включит сам.
5. **Установка.** `bash $DUO_HOME/install.sh --systemd` (идемпотентно, ЗАМЕНЯЕТ ранее поставленный
   `duo-supervise.*`; прежние юниты сохраняются как `*.bak-<время>`). Проверка:
   `systemctl --user list-timers 'duo-supervise*' --no-pager` и `journalctl --user -u duo-supervise.service -n 5 --no-pager`.
6. **Отключение/откат.** `systemctl --user disable --now duo-supervise.timer`; вернуть прежние юниты —
   положить `*.bak-<время>` на место и `systemctl --user daemon-reload`.

## Что делать при остановке (шпаргалка помощника)

```bash
duo status --task X          # halt.kind, stop_reason, процесс
duo run --task X --resume    # transport / crash / artifact_missing
duo run --task X --resume --wait-quota   # квота провайдера (halt cause=quota): сам дождётся сброса
duo run --task X --resume --add-iterations 3   # limit
duo run --task X --resume --add-budget 40      # budget
```

Подробно по видам остановок — `docs/CHEATSHEET-CONTROL.md` («Остановки»).

## Если сломалось

- `systemctl --user status duo-supervise.timer` — состояние; таймер не стреляет → `loginctl show-user $USER -p Linger`
  (должно быть `yes`; включить: `sudo loginctl enable-linger $USER`);
- алерты не приходят на рабочий стол → у user-сервиса нет D-Bus: проверь
  `systemctl --user show-environment | grep DBUS`; в `duo-supervise.service` задан
  `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/%U/bus`;
- хочется «просто посмотреть»: `supervise --dry-run` и `status --all`;
- оркестратор, запущенный надзором, остаётся в cgroup службы (`Unit process … remains running after unit stopped` в журнале) и
  без лимита памяти — для изоляции включить `parallel.isolate_cgroup` (+ `memory_max`) в конфиге проекта: надзор возобновляет серию
  тем же `run_detached`, поэтому она пойдёт в собственной области (Н51).

## Другие «вечные» сторожа (ночные калибровки и т.п.)

Паттерн прежний, но с поправкой на урок systemd: одноходовка «жив ли цель → нет: перезапустить» под
`Type=oneshot` обязана иметь `KillMode=process` (или запускать цель через `systemd-run --user --collect`),
быть идемпотентной (`flock`) и проверять **результат** перезапуска не по `pgrep` через 3 секунды, а по
устойчивому признаку (замок/heartbeat цели).
