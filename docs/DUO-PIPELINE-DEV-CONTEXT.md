## 1. Что такое инструмент (минимум для входа)

**Оркестратор «исполнитель ↔ ревью»** для любых git-проектов: один файл `duo_pipeline.py` (≈ 7500 строк) плюс
`audit_cmd.py`, `accept_cmd.py`, `archive_cmd.py`, `reset_cmd.py`, `provision_worktree.py`. Модель вызывается как
`claude -p … --output-format stream-json --verbose` через профиль CLI (`claude_config_dir`, шлюз к GLM).

| режим | кто | фазы |
|---|---|---|
| `solo` | один исполнитель на дешёвой модели (`haiku` → glm-5.3-flash) | без плана и ревью; цикл вызовов одной сессией до маркера `SOLO_DONE` |
| `pair` | исполнитель + **один** проверяющий | план → ревью плана → код → ревью кода, до ACCEPT |
| `duo` | исполнитель + два критика вслепую + председатель | то же, но ревью — дуэт с синтезом председателя |

Изоляция: `shared` (основное дерево) или `worktree` (своя ветка `duo/<task>` и дерево `.worktrees/<task>`;
параллельные серии; зона записи `## files_touch` плана). Артефакты серии — `pipeline/<task>/` (`task.md`, `plan_vN.md`,
`revNNN_*.md`, `impl_report_vN.md`, `state.json`, `orchestrator.log`, `transcripts/`). После ACCEPT человек (или
оператор) идёт по цепочке: `audit` → `commit-by-plan` (--dry-run → --yes) → `gates` → (worktree) `merge`.

Конфиг слоями: `DEFAULTS` в коде < `config.json` инструмента < `<проект>/.duo/config.json` (словари сливаются по
ключам, списки заменяются); `guard_config_problems` проверяет форму. Надзор — systemd-таймер `duo supervise`
(реестр проектов `~/.config/duo-pipeline/projects.json`).

**Карта документации:** `docs/CHEATSHEET-CONTROL.md` (команды и грабли; раздел «Восстановление серии и защиты…»),
`docs/CHEATSHEET-WATCHDOG-FAILSAFE.md` (надзор), `docs/PROJECT-SETUP.md` (ключи проектного конфига),
`docs/FIELD-TEST-BRIEF.md` (бриф полевых проверок: оператор + контролёр), `skill/SKILL.md` (скилл для агентов).

**Стенды.** NVIDIA — основной стенд разработки; AMD — второй, ставится `git pull --ff-only` в `~/duo-pipeline`.
Профили моделей (`~/.claude-glm/settings.json`: алиасы `opus/sonnet/haiku`) обновляются на стендах **независимо**;
`model_expect` в конфиге только предупреждает о расхождении. На AMD профиль в последний раз сверяли до выхода
glm-5.4 — перед использованием там выполнить `duo selftest` (платный, ≈ $0.1 на модель).

### 2.2 Тракт ревью и классы сбоя доставки (Н38, **новое**)

Раньше любой ответ ревьюера, не похожий на отчёт, назывался «неполный отчёт» и повторялся с припиской «выведи
ПОЛНЫЙ отчёт». Теперь каждая непринятая попытка классифицируется (`classify_failure(text, meta)`), и реакция зависит
от класса:

| класс | признак | реакция | цена попытки |
|---|---|---|---|
| `transient` | `API Error: 529 … overloaded`, `timed out`, статусы 429/500/502/503/504/529 | **пауза** `api_retry_wait_sec × 2^(k−1)` (30/60/120/240 с), тот же промпт, счётчик `limits.overload_retries` (4); исчерпано → `ReviewIncompleteError(kind="transport")` → `halt transport` (авто-возобновляется надзором) | $0 |
| `output_limit` | `API Error: … exceeded the 32000 output token maximum` либо `stop_reason == "max_tokens"` | **один** повтор с `effort` на ступень ниже (`lower_effort`) + приписка «думай коротко» (+ `CLAUDE_CODE_MAX_OUTPUT_TOKENS=64000`, если ниже); затем `ReviewIncompleteError(kind="review_incomplete")` → `halt review_incomplete` (решение человека) | $3–5 |
| `api_error` | прочая `API Error` | повтор без приписки (приписка про формат бессмысленна), затем `halt transport` | обычно $0 |
| `stub` | пусто / `ExitPlanMode` / заглушка | повтор с припиской про инструменты планирования (`CHAIRMAN_MAX_ATTEMPTS`) | мало |
| `format` | текст пришёл, но не `# rev —` + `VERDICT` | повтор с припиской «выведи ПОЛНЫЙ отчёт»; исчерпание — последний текст уходит в fallback как раньше | как обычный вызов |

**Склейка.** Если лимит вывода разрезал отчёт на несколько сообщений, `claude` CLI сам «продолжает» ход **новым
сообщением**, а `result.result` хранит только последнее (в замере 791 из 2002 знаков текста). Транспорт копит
`meta["tail_msgs"]` (тексты сообщений после последнего `tool_use`), `stitch_messages` склеивает их (дедуп стыка по
первой строке ≥ 12 знаков через `rfind`), и склейка принимается, только если проходит `_valid_report`. Журнал: `СКЛЕЙКА`.
**На живом потоке эта ветка не воспроизведена** — см. раздел 7.

Ключевые функции (все в `duo_pipeline.py`): `classify_failure`, `lower_effort`, `stitch_messages`,
`ClaudeGlm.call(..., effort="", env_extra=None)` + `take_call_meta()`, `ClaudeGlm._base_env(mode, extra)`,
`DuoReviewer._chairman_with_retry`, `DuoReviewer._reviewer_call`, `_pause_transient`, `_limit_retry_extra`,
`_attempt_note`, `_final_note`, `DuoReviewer.review` (тонкая обёртка над `_review_impl`: вешает `e.review_cost` на **любое**
исключение), `Pipeline._charge_review` (цена оборванного ревью → `spent_usd` до `halt`), `ReviewIncompleteError`.
Сигнатура `ClaudeGlm.call` по возвращаемому значению не менялась: `(text, session_id, cost)`.

### 2.4 Телеметрия и семантика денег

- `review_telemetry[]` и `status --json` → `review_transport` теперь содержат, помимо `stub_retries`/`transport_retries`:
  `incomplete_retries`, `overload_retries`, `limit_retries`, `stitched` (Н39: у `pair` ретраи раньше не считались).
- В журнале у каждой непринятой попытки: «попытка N не принята — класс X, $cost, рассуждений N знаков (пик ≈T ток.), сообщений N».
  В шапке `*_attemptN.md` — `класс=…; stop_reason=…; сообщений=…; рассуждений=… знаков (пик ≈… ток.); api_error_status=…`.
- **Семантика `cost=` в шапке итогового транскрипта ревью — КУМУЛЯТИВ всей цепочки вызовов шага** (включая отброшенные
  попытки). `*_attemptN.md` — цена одной попытки и она **уже входит** в итоговую. Складывать «итоговый + attempt» — двойной
  счёт (в полевом отчёте так считали). Шапка итогового транскрипта теперь так и помечена (`_final_note`). Истина по деньгам —
  `state.spent_usd` (`status --json` → `budget.spent_usd`); с Н42 в нём есть и цена ревью, оборванного исключением.
- Мягкий лимит бюджета: проверяется на **границе итерации** (после ревью в полёте), `budget_grace_usd` — запас.

### 2.6 Факты о потоке `claude -p --output-format stream-json --verbose` (замерено, CLI 2.1.215)

- Одно событие `assistant` на **блок** содержимого (thinking / text / tool_use), группировка — по `message.id`.
  `assistant.message.stop_reason` в потоке всегда `None`; настоящие `stop_reason`, `is_error`, `api_error_status`, `subtype`,
  `terminal_reason`, `num_turns`, `total_cost_usd` — только в событии `result` и в журналах сессий

- Пока модель думает, поток заливается событиями `{"type":"system","subtype":"thinking_tokens","estimated_tokens":N,

- На `max_tokens` CLI продолжает ход новым сообщением (в замере `num_turns=15`, 13 сообщений, `result.result` — только хвост).
- Размеры рассуждений ревью на glm-5.4/high в бою — **105–118 тыс. знаков** на финальный синтез, 3–9 мин на вызов.

## 5. Стратегия доработок

### 5.1 Принципы (вынесены из восьми волн отчётов)

1. **Лечить причину доставки, а не симптом формата.** Сначала классифицировать отказ по данным (`RESPONSE`, `stop_reason`,
   журнал сессии), потом решать, что менять; промпт — последним.
2. **Деньги — первый класс данных.** Каждая операция, тратящая деньги, должна быть видна в `status --json` без чтения
   транскриптов; «счётчик» и «транскрипты» не должны расходиться (Н42).
3. **Ошибки пользователя инструмента — тоже дефекты бриф+инструмент.** Из 10 ошибок контролёра волны 1 (К6–К15) большинство
   предотвратимы либо брифом, либо предупреждением инструмента; правило — каждую К разбирать на «бриф / инструмент / оба».
4. **Не лечить то, чего не видели в бою, дорогим механизмом.** Отклонены ранее: preflight-кэш, автокопирование журналов
   сессий, автоповтор шагов приёмки. Здесь: не резать glob-спаны парсером (Н43), не менять rc `gates` без решения (К11).
5. **Любое изменение — с мутационной проверкой тестов** (раздел 2.7) и с обновлением трёх мест: код+тесты, шпаргалка,
   бриф (строка «как проверить в бою» в п. 4.3).
6. **Калибровку считать на данных волн, а не синтетике**: синтетика — для механизма (формат, поток), не для цены и качества.

### 5.2 Очередь работ

**P1 — ближайшее, малые/средние, высокая отдача**

- **P1-1. Журнал вызовов (`cost ledger`).** Источник правды по деньгам без транскриптов: в `state.json` (ограниченный список)
  и в `status --json` → `budget.ledger`: каждый вызов модели — роль/персона, фаза, тег, цена, класс исхода
  (`accepted | rejected:<класс>`), время, `thinking_tokens_peak`; суммы «принято / отвергнуто». Закрывает Н42 «до конца» (счётчик
  = сумме), даёт калибровку (цена ревью по медиане и хвосту), основа для P2-1 и P2-2. Критерий готовности: на тестовой серии
  сумма журнала = `spent_usd`; остановка по исключению не теряет запись. Риск: рост `state.json` — ограничить N последними +
  агрегаты.
- **P1-2. Вынести рабочие инструменты разработчика в репозиторий.** Сейчас мутационный прогон и синтетический зонд живут в
  `/tmp` и теряются между сессиями. Положить `dev/mutate.py` (каталог вне `tests/`, не запускается `pytest`) и
  `dev/probe_transport.py` (приложение B); в `CLAUDE.md` указать, что они зовут модель (`probe`) и потому не часть CI.
  Критерий: `dev/mutate.py --list` показывает мутации, базовый прогон зелёный; хостит правила гигиены (`PYTHONDONTWRITEBYTECODE`).
- **P1-3. Проверить Н38 в бою (не код, а испытание).** Следующая волна на glm-5.4/high обязана подтвердить: `limit_retries == 0`
  на ≥ 10 ревью при 64000; каждая оборванная попытка имеет класс; пульс Н40 виден на каждом ревью дольше 2 мин. Критерии
  провала — раздел 6.2.

**P2 — средние, после данных волны 2**

- **P2-1. Калибровка `effort` по ролям и фазам.** Сейчас `effort` — по алиасу модели (`opus: high` для всех ревью). Гипотеза: ревью
  *плана* (мало кода, много логики) дешевле на `medium`, ревью *кода* — на `high`. Реализация (если A/B подтвердит): ключ
  `effort_by_role` (`{"plan": "medium", "impl": "high"}`) поверх `effort` по алиасу. Требует P1-1 для измерения.
  **Решение владельца** — не менять дефолт `high` без A/B (протокол — в брифе, п. 4.6).
- **P2-2. Оценка стоимости до запуска.** `duo run` печатает «ориентир по бюджету» из ledger прошлых серий проекта (медиана цены ревью ×
  ожидаемые итерации + исполнитель) и предупреждает, если `limits.budget_usd` серии < ориентира (К10: $24 при нужных $45).
  Только предупреждение.
- **P2-3. Надзор с различением причин остановки** (*для квоты — сделано, Н46/Н58; для перегрузки `transient` — нет*). Для `halt transport` по классу `transient` (перегрузка провайдера) —
  возобновление с растущей паузой 10–15 мин до окна N часов, **не расходуя** `max_resumes` (сейчас контролёры пишут свои циклы
  `duo wait` → пауза → `--resume`). Для `review_incomplete`/`review_empty` — не возобновлять никогда. Требует поля `halt.cause`.
- **P2-4. Зона записи solo (Н36).** Токен `@task` в `audit.write_zones`: зона из секции `## files_touch` самого `task.md`
  (тем же парсером, что у плана). Критерий: solo-серия с `files_touch` в задании даёт 0 ложных нарушений. Риск: авторы
  `task.md` не всегда пишут секцию — тогда токен «не раскрыт» (как сейчас), без деградации.
- **P2-5. `gates` по бейзлайну (К11).** Решить: оставлять rc=0 с двойным предупреждением или вернуть отдельный код (3) для
  «зелёный по бейзлайну, не по коду серии». Довод «за»: ложная уверенность опаснее лишнего кода; «против»: для shared-серий с
  посторонним WIP в дереве предупреждение срабатывает шумно (счёт `dirty_n` включает чужие файлы). Нужен срез: сколько раз
  предупреждение было ложным. **Решение владельца.**
- **P2-6. `duo report` — заготовка отчёта из данных.** Команда печатает для серии markdown-скелет: режим/изоляция/модели, время
  начала/конца (из лога), `spent_usd`, итерации и вердикты, `review_transport`, **таблица непринятых попыток** (время, класс,
  цена — из ledger/транскриптов), снимок `status --json`. Убирает класс ошибок К12 (время «по ощущению») и К14 (класс по памяти)
  и сокращает ручную работу оператора. Бриф (раздел 6) тогда требует «приложить вывод `duo report`».

## Приложение B. Рецепт синтетического зонда (не часть CI — зовёт модель, платный)

Задача зонда — получить сырой поток `stream-json` и по событиям посчитать: сообщения, размеры блоков `thinking`/`text`, пик
`thinking_tokens`, `stop_reason`/`cost`/`num_turns` из `result`. Основа:

```python
# probe.py NAME --effort high --max-out 64000 --prompt-file F  (кладёт сырой поток в /tmp/synth/raw_NAME.jsonl)
import json, os, subprocess, sys, time
from pathlib import Path

env = dict(os.environ, CLAUDE_CONFIG_DIR=str(Path.home() / ".claude-glm"), NO_COLOR="1")
# env["CLAUDE_CODE_MAX_OUTPUT_TOKENS"] = "64000"   # по необходимости
cmd = ["claude", "-p", "--model", "opus", "--effort", "high",
       "--output-format", "stream-json", "--verbose", "--permission-mode", "plan",
       Path(sys.argv[1]).read_text(encoding="utf-8")]          # prompt-file
t0 = time.time()
p = subprocess.run(cmd, cwd="/tmp/synth/work", env=env, capture_output=True, text=True, timeout=600)
think = text = peak = 0
msgs, res = set(), {}
for line in p.stdout.splitlines():
    ev = json.loads(line)
    if ev.get("type") == "assistant":
        m = ev["message"]; msgs.add(m.get("id"))
        for b in m["content"]:
            think += len(b.get("thinking") or "") if b.get("type") == "thinking" else 0
            text += len(b.get("text") or "") if b.get("type") == "text" else 0
    elif ev.get("type") == "system" and ev.get("subtype") == "thinking_tokens":
        peak = max(peak, ev.get("estimated_tokens") or 0)
    elif ev.get("type") == "result":
        res = ev
print(f"{time.time()-t0:.0f}s msgs={len(msgs)} think={think} text={text} peak_tok={peak} "
      f"stop={res.get('stop_reason')} cost={res.get('total_cost_usd')} turns={res.get('num_turns')}")
```

Правила: бюджет-ограничитель (единицы $), токены в поток не попадают, профиль — тот же, что у серий; результаты сверять с

## Приложение C. Рабочие процедуры разработчика

**Гейт:** `make check PY=/путь/к/python` (≥ 3.11 с `ruff` и `pytest`). Свой `-q` не добавлять.

**Мутационная проверка (ручной скрипт; P1-2 — положить в репозиторий).** Список троек `(файл, имя, старый, новый)`; для каждой:
записать мутировавший файл, удалить `__pycache__`, прогнать `pytest -x -q -p no:cacheprovider` по релевантным тестам с
`PYTHONDONTWRITEBYTECODE=1`, вернуть оригинал в `finally`. Мутация «выжила» (тесты зелёные) — написать тест, который её убивает.
Типовые мутации: инверсия условия, `<`→`<=`, удаление вызова (`beat(...)`, `self._acc(...)`), подмена литерала, смена `fullmatch`→`match`.
Побочная польза: ловит **тесты, кодирующие дефект** (старый тест требовал тишины пульса при живом потоке).

**Чистая копия:** `git archive HEAD` + ваши файлы в временный каталог, без `.git`-состояния и локальных файлов — проверка, что
репозиторий самодостаточен (в частности, гигиена публичного репозитория).

**Коммит/доставка:** явный список файлов (`docs/reports/` и `githubtoken.md` не добавлять), `git push origin main`, на втором
стенде `git pull --ff-only` и `python3 -c "import duo_pipeline"`; профиль CLI второго стенда **не трогать** (отдельная
ответственность владельца).

**Нумерация.** Н — находки инструмента (сквозная: последняя — Н59; следующая — Н60), К — ошибки контролёра
(последняя — К25; следующая — К26), Г — гипотезы (раздел 6.2, последняя — Г14), P — очередь работ (раздел 5.2).

**Источники истины по чужим сериям:** `pipeline/<task>/orchestrator.log` (события), `transcripts/` (промпт и ответ каждого вызова;
шапка — класс/цена), `state.json` (только чтение), журналы сессий CLI. Не доверять пересказу оператора и «ощущению» времени.
