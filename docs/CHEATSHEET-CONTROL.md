# Шпаргалка 1: управление duo-пайплайном (pipev5 + pipemodes + duoportable)

Оркестратор: `$DUO_HOME/duo_pipeline.py` (`$DUO_HOME` — каталог клона репозитория инструмента; конфиг —
`config.json` инструмента + `.duo/config.json` подключённого проекта).
Артефакты каждой серии: `pipeline/<task>/` В САМОМ ПРОЕКТЕ. Ниже `duo` —
вызов оркестратора: лаунчер `bin/duo` (ставится `bash $DUO_HOME/install.sh`
в `~/.local/bin/duo`); развёрнуто —
`python $DUO_HOME/duo_pipeline.py <команда>`.
Полный формат — `CLAUDE.md` репозитория инструмента; подключение проектов и
ключи `.duo/config.json` — `docs/PROJECT-SETUP.md`; здесь — рабочие команды
без воды.

## СТОРОЖА: не пропусти конец фазы

Серия идёт в фоне (`run` отпускает консоль), а конец фазы — **тихий**: «план принят» (`impl_pending`) и
«код принят» (`done`) никто не объявляет, пока вы не следите; `impl_pending` вдобавок не стартует сам. В полевых
отчётах 19 и 20.11.2026 оператор четырежды не держал ожидание — серия простаивала по 17–20 минут.

1. **В ту же минуту после каждого `run` / `run --continue`** запусти сторожа В ФОНЕ:
   `duo wait --task X --timeout 3600 --quiet`; агенту — с `notify_on_output` по `WAIT-RESULT`. Итог —
   `WAIT-RESULT: done | impl_pending | halted | dead | idle | timeout` (коды выхода 0/0/10/11/12/13). Команду
   печатает сам `run` — блоком «СТОРОЖ».
2. `nohup duo wait … > файл &` без наблюдения за файлом **молчит**: сторож, которого никто не читает, не сторож.
3. Каждый `WAIT-RESULT` — повод действовать сразу: `impl_pending` → прочесть план и решить про `--continue`;
   `done` → `gates`/`accept`/`audit`; `halted`/`dead` → `status`, затем `--resume` или `set-verdict`.
4. Вторая страховка — **надзор** (`duo-supervise.timer`, ≤ 2 мин): критичное уведомление рабочего стола о
   `done`/`impl_pending`/остановке, если проект подключён (`duo projects`) и `notify.desktop` включён. Он пишет
   НЕ в `orchestrator.log`, а в журнал systemd: `journalctl --user -u duo-supervise.service | grep SUPERVISE`
   (искать суффикс `| уведомление: принято демоном…`). Проект подключён с `setup --no-register` — сторож один: ваш `wait`.
5. Вернулся в сессию или потерял сторожа (рестарт агента, обрыв ssh) — первым делом `duo status --task X`
   (или `--all`): строки `ЖДЁТ ВАС N мин` (план принят / остановка) и `ЗАВЕРШЕНА N мин назад` скажут, сколько серия
   уже стоит.

## Запуск из любого проекта (duoportable)

- **Корень проекта (R1)**: `--repo PATH` > `DUO_REPO` > legacy-ключ `repo`
  конфига `--config` > автодетект от cwd (из любого подкаталога и linked
  worktree). Обычно достаточно запустить команду из каталога проекта.
  `duo setup` в каталоге проекта подключает его (каркас `.duo/config.json`,
  записи `.gitignore`, регистрация в реестре надзора).
- **Конфиг (R2)**: `DEFAULTS < config.json инструмента < <проект>/.duo/config.json`;
  списки замещаются целиком; пути терпят `~`/`$VAR`.
- **Гейты (R3)**: шаги `gates.steps` проектного конфига (`{py}/{pybin}/{cpus}`);
  `duo gates --task X` гоняет их в чистой копии. Пример набора — в
  `docs/PROJECT-SETUP.md`. Как гейты соотносятся с CI проекта и CI самого инструмента —
  раздел «CI и гейты» ниже.
- **Надзор (R8)**: `duo supervise` без явного корня обходит РЕЕСТР проектов
  (`duo projects` — таблица/`--add/--remove/--prune`); уведомления помечены
  `duo <проект>/<task>`. С явным `--repo`/`DUO_REPO` — один проект.
- **Worktree-ресурсы (R4/R7)**: `git.worktree_links` — что симлинкается в
  worktree (`.env` — никогда); `executor_worktree_note` — приписка «не
  перезапускать X» в промпт исполнителя.

## CI и гейты: три контура и кто их потребитель

После переноса оркестратора в отдельный репозиторий (этап 2 duoportable) проверок три. Они не
заменяют друг друга: красный в одном контуре ничего не говорит о другом.

| контур | что проверяет | где определён | кто потребитель (кому красный) | когда запускается |
|---|---|---|---|---|
| **1. CI проекта** (напр. GitHub Actions `.github/workflows/ci.yml`) | код ПРОЕКТА: lint, unit, integration, фронт и т. д. Код оркестратора НЕ проверяет | в проекте: `.github/workflows`, `Makefile` | разработчики проекта; по красному владелец решает, сливать ли | push рабочей ветки и PR; ветки `duo/**` в origin не пушатся |
| **2. Гейты серии** (`duo gates --task X`) | локальная копия контура 1: те же команды в чистой копии `git archive` + заглушки проекта `gates.stubs` (роняют тяжёлые модули при импорте, как раннер CI) | проектный `.duo/config.json` → `gates.steps` | тот, кто принимает серию (эксперт/человек): ACCEPT ревьюера ≠ гейты воспроизведены | после принятой имплементации, ДО `commit-by-plan`/`merge` (`merge --dry-run` напомнит) |
| **3. CI инструмента** (`make check` в duo-pipeline: ruff + pytest `tests`) | сам оркестратор, установщик, лаунчер | репозиторий инструмента: `Makefile`, `.duo/config.json` (тот же прогон = `duo gates --task X` в этом репо) | КАЖДЫЙ проект, подключённый к инструменту: красный здесь = риск для всех | перед каждым коммитом в duo-pipeline; GitHub Actions в репозитории нет, другого гейта у инструмента нет |

Правила:

1. **Тесты оркестратора принадлежат контуру 3.** Проект их больше не содержит, его CI их не
   исполняет (до выноса оркестратора проект гонял их в своём `make unit`).
   Серия проекта оркестратор не меняет (он вне её дерева); меняется оркестратор серией
   ВНУТРИ репозитория инструмента: `duo --repo $DUO_HOME run --task X`
   (dogfooding), гейты — `make check`.
2. **Контур 2 обязан зеркалить контур 1.** Правите `Makefile`/workflow проекта — в том же
   коммите правите `gates.steps`. Расхождения допустимы осознанно: гейты могут быть строже CI
   (напр. шаг `lint-imports`, которого нет в CI) и уже CI (Python-only: фронтенд,
   Go-клиент, `openapi-drift`, GPU-workflow гейты серии не покрывают — для серий в этих областях
   соответствующие проверки CI прогоняются вручную). Таблицу соответствия «шаг гейтов ↔ job CI»
   удобно вести в шпаргалке самого проекта.
3. **Единственный контракт между проектом и инструментом, закреплённый тестами с двух сторон, —
   охрана архива** (`duo archive` повторяет сканирование охранного теста проекта
   `tests/arch/test_archived_series_refs.py`; проектные значения — `archive.guard_*` в
   `.duo/config.json`). Литералы пинятся в `tests/unit/test_duo_archive.py` инструмента и в
   `tests/arch/test_archive_guard_config_sync.py` проекта: красный с любой стороны = вторая
   сторона разошлась, правятся оба репозитория.
4. **Надзор (`supervise`, systemd-таймер) — не CI**: он следит за ЖИВЫМИ сериями всех проектов
   реестра (dead/halted → алерт и авто-возобновление), код и тесты не проверяет.
5. **Кого запускать:** правка кода проекта → CI проекта и `duo gates`; правка оркестратора →
   `make check` в duo-pipeline; правка `gates.steps`/`archive.*` проекта → `duo gates --dry-run`
   (план команд) и тест охраны проекта.

## Три режима серии

| режим | кто работает | стадии | кто проверяет | вызовов модели на итерацию ревью | как включить |
|---|---|---|---|---|---|
| **duo** (по умолчанию) | исполнитель + председатель + дуэт | план → код | план: `socrates2` + `feynman2`; код: `torvalds2` + `meadows2` (`duo.members_*`) | 7 (R1×2, R2×2, R3×2, председатель) | — |
| **pair** | исполнитель + ОДИН проверяющий | план → код | план: `feynman2`; код: `torvalds2` (`pair.reviewer_plan/impl`) | 1 | `--mode pair` |
| **solo** | один исполнитель (`solo.model` = `haiku` → `glm-5.3-flash`) | только код (без плана) | никто | — | `--solo` |

Режим и изоляция (см. «Параллельные серии») **записываются в `state.json` при первом запуске**:
`run --continue`, `run --resume`, сторож (`supervise`), `commit-by-plan`, `merge` берут их оттуда —
повторять `--mode`/`--worktree`/`--config` не нужно. Исключение — `solo`: он каждый раз просится
флагом `--solo` (меняет модель и запрещает ветку), из state молча не подхватывается и применим
только к серии в `phase=plan|solo`.

## Режим pair: исполнитель + один проверяющий

```bash
duo init --task <name> --mode pair     # или передать --mode pair в run
duo run --task <name>                  # стадия «план»: пока проверяющий не примет
duo run --task <name> --continue       # стадия «код»: пока проверяющий не примет
```

- Стадии те же, что в duo: план (`plan_vN.md`) → пауза `impl_pending` → код (`impl_report_vN.md` + дифф);
  на каждой стадии проверяющий выносит `VERDICT: ACCEPT|REVISE`, REVISE возвращает исполнителю
  на доработку, цикл идёт до приёмки (или до лимита итераций/бюджета, как в duo).
- Проверяющий пишет итоговый отчёт сам (тот же формат `revNNN_<фаза>.md` с машинной последней строкой
  `VERDICT:`), поэтому `set-verdict`, `rework`, `errata`, антиповторы отклонённых замечаний, `commit_plan`
  работают без изменений. Персоны — «2»-версии (`council-feynman2`, `council-torvalds2`); под единственного
  проверяющего им добавляется блок правил (STANCE = итоговый вердикт, слепую зону проверить явно перед
  вердиктом), чек-листы пре-регистрации плана и «эрраты реализованы, иначе блокер» — те же, что у председателя.
- Какие персоны — правится в `config.json` → `pair.reviewer_plan` / `pair.reviewer_impl` (имена файлов
  `council-<имя>.md` в `council_agents_dir`; `selftest` их проверяет). Выбор по умолчанию: план проверяет
  `feynman2` (исполним ли план буквально, сходятся ли числа), код — `torvalds2` (делает ли код буквально
  то, что обещали план/эрраты/отчёт, честны ли тесты и отчёт).
- Когда брать: средние по риску задачи, где дуэт — перебор (дешевле и быстрее: 1 вызов вместо 7). Главная
  цена — слепая зона одного рецензента; для критичных/необратимых изменений (схема БД, конвейер данных) —
  duo. Режимы можно сменить между стадиями: `run --task X --mode duo --continue`.

## Полный цикл (исполнитель ↔ дуо-надсмотрщик; модели по ролям — раздел «Модели по ролям»)

```bash
cd /путь/к/проекту                   # любой проект, подключённый `duo setup` (или автодетект корня)
# 1. создать задачу (task.md положить/написать в pipeline/<task>/)
duo init --task <name>
# 2. запустить (detached — переживает терминал; ветка duo/<name> сама)
duo run --task <name>
# 3. после ACCEPT плана — продолжить в имплементацию
duo run --task <name> --continue
# 4. после ACCEPT имплементации — разложить коммиты по commit_plan
duo commit-by-plan --task <name> --yes
```

## Упрощённый solo-режим (дешёвая модель glm-5.3-flash, БЕЗ плана и ревью)

Для артефактных/измерительных задач, где дорогое планирование избыточно.

```bash
duo init --task <name>   # task.md обязателен
duo run --task <name> --solo
```

Как работает:
- исполнитель = `haiku` → **glm-5.3-flash** (конфиг `solo.model`; алиас — слой профиля CLI, см. «Модели по ролям»);
- план-фаза и дуо-ревью пропускаются, ветка НЕ создаётся;
- цикл вызовов одной сессией (лимит `solo.max_turns`, по умолчанию 24):
  длинные фоновые операции (скачивание) исполнитель запускает и
  контролирует в следующих вызовах;
- завершение: маркер `SOLO_DONE` — **строго последней строкой ответа**
  исполнителя + строка `## SOLO_DONE` в конце `pipeline/<task>/solo_report.md`;
- прогресс читать в `pipeline/<task>/solo_report.md` (разделы «вызов N»);
- **solo + `--worktree` (Н35):** серия доходит до `main` через `commit-by-plan` → `gates` → `merge`, а `commit-by-plan` читает `impl_report_vN.md` с секцией `## commit_plan`. В промпт solo-исполнителя worktree-серии пайплайн сам добавляет просьбу: в последнем вызове, перед `SOLO_DONE`, записать `pipeline/<task>/impl_report_v1.md` (что сделано, файлы, проверки) с четырёхколоночным `commit_plan` (формат — как у pair/duo; каждый путь в своих бэктиках через запятую). `impl_version` у solo остаётся 0, поэтому `commit-by-plan` без `--version` берёт **самый свежий** `impl_report_vN.md` серии, если файла заданной версии нет (печатает «версия отчёта не задана … беру …»); явный `--version N` не подменяется. В shared просьбы нет (коммитит человек). Полевое подтверждение: строки «пиши `impl_report_v1.md` с `commit_plan`» в `task.md` хватало, чтобы исполнитель на flash сам сделал отчёт — теперь это не зависит от того, вспомнил ли составитель задания;

Протокол выучен на ошибках (не ломать): при входе в solo оркестратор сам
стирает маркер прошлой серии; task.md передаётся ЦЕЛИКОМ (аддендумы в
конце файла — рабочий механизм продления серии после `done`: допиши
раздел «Аддендум A», сбрось `state.json` → `phase: plan`, убери
`executor_session`/`solo_turn`, удали `.lock`, запусти `run --solo` снова).

## Серии на живом оборудовании (телефон, GPU, порт, эмулятор)

Полевой отчёт 20.11.2026: solo-серии управляли реальным устройством в общем дереве. Исполнитель идёт с
`--dangerously-skip-permissions`, поэтому «НЕ делай X» в `task.md` — лишь просьба, а не граница. Для таких
проектов в проектном слое (`.duo/config.json`) собирается «профиль live» — это **набор ключей**, а не флаг:

```json
{
  "executor_deny": ["Bash(adb:*)", "Read(./.env)", "Edit(./config/**)"],
  "resources": ["adb:phone-1"],
  "acceptance": {"steps": [
    {"name": "status", "argv": ["python3", "cli.py", "status", "--device", "all"], "inconclusive_rc": 2}
  ]},
  "audit": {
    "deny_bash": ["\\badb\\b"],
    "deny_read": ["(^|/)\\.env$"],
    "deny_script": ["subprocess|os\\.system|\\badb\\b"],
    "write_zones": ["pipeline/{task}/", "runs/", "@plan"]
  },
  "supervisor": {"auto_resume": false}
}
```

| механизм | что делает | чего НЕ делает |
|---|---|---|
| `executor_deny` (список правил) | правила `--disallowedTools` claude CLI передаются **исполнителю** (ревьюеры и так read-only): запрещённый вызов инструмента CLI отклоняет **технически**, даже в bypass-режиме (проверено на CLI 2.1.215). Синтаксис правил — CLI: `Bash(префикс:*)`, `Read(./путь)`, `Edit(./каталог/**)`. `status` печатает «технических запретов: N» или «нет — только текст промпта»; в лог серии — строка `ИСПОЛНИТЕЛЬ: технических запретов N` | не защищает от обхода через интерпретатор: `python -c "import subprocess…"`, `bash -c`, записанный и запущенный скрипт обходят префиксные правила Bash. Это **ограда от ошибок, не от злого умысла**; настоящая изоляция — права ОС. Запятая внутри правила недопустима (правила склеиваются запятой в один аргумент) — `run` откажет с пояснением |
| `duo audit --task X [--json] [--archive]` | read-only разбор журнала сессии исполнителя (`<claude_config_dir>/projects/*/<id>.jsonl`; id — `state.json`: `executor_sessions`, `executor_session`): счётчики вызовов по инструментам и нарушения правил `audit` (`deny_bash` — regex по тексту Bash-команд, `deny_read` — по путям Read, `deny_script` — по **телу записанных `.py`/`.sh`**, `write_zones` — каталоги, куда писать можно, `{task}` подставляется; токен `@plan` — ещё и зона из `## files_touch` принятого плана: файлы, каталоги, globs; запись по **реальному** пути каталога артефактов — у worktree-серии `pipeline/<task>` это симлинк на основное дерево — внутри разрешённой зоны не нарушение (Н41: проверка разворачивает `realpath` зоны, остальное основное дерево по-прежнему «вне дерева серии»)). Код выхода: **0** чисто, **1** нарушения, **2** проверить нельзя («журнал не найден» ≠ «чисто»: CLI чистит старые сессии) | не блокирует и не меняет серию; не видит, что делал запущенный исполнителем скрипт (отсюда `deny_script`), и не включает журналы ревьюеров. Тела `.md` не сканируются намеренно: в отчётах исполнитель пишет «прямого adb не было» |
| `duo audit --archive` | копия журналов в `pipeline/<task>/audit/` (gzip, права 0600, свой `.gitignore` `*`) — чтобы сессия пережила чистку CLI | **не по умолчанию**: журнал содержит РЕЗУЛЬТАТЫ инструментов — содержимое прочитанных файлов и вывод команд, то есть секреты. Не коммитить, не выкладывать |
| `resources` (список имён) | серия берёт машинные замки `flock` на **всю жизнь `run`**; вторая серия на том же ресурсе получает `ОТКАЗ` с именем держателя (проект/серия/pid/время) **до** любых правок state и дерева. `run --wait-resources SEC` — ждать освобождения. `status` показывает «ресурс X: свободен / ЗАНЯТ — серия …». Замки берутся в алфавитном порядке (пересекающиеся наборы не заклинят друг друга) | не угадывает железо: ресурс — договорённость по имени. Замки живут в `${XDG_STATE_HOME:-~/.local/state}/duo-pipeline/resources/<имя>.lock` (символы вне `A-Za-z0-9._-` → `_`) — **локально для машины**. Внешний скрипт, не берущий замок, ничего не знает: `flock <файл>.lock -c '<команда>'` ставит его в ту же очередь (в `status` он виден как «внешний процесс») |

**`supervisor.auto_resume`.** В `config.json` инструмента стоит `true`: при сбое транспорта/крэше надзор САМ
перезапустит серию (потолок — `max_resumes`). Для проектов, где повторный запуск исполнителя снова трогает
железо, ставьте `false` в проектном слое — тогда остаются только алерты, возобновление — решением человека.

**Живая приёмка: `duo accept --task X [--dry-run] [--json] [--wait-resources SEC]`.** `gates` для такого проекта
бесполезны (чистая копия `git archive`: устройств, сети и ключей в ней нет), а `done` значит лишь «исполнитель
заявил `SOLO_DONE` / ревью приняло», не «на устройстве работает». `acceptance.steps` — шаги проекта в формате
`gates.steps` (`argv` — список, без shell; опционально `name`, `timeout_sec` — по умолчанию 600, `inconclusive_rc`
— код, означающий «устройство недоступно», и `inconclusive_match` — regex по выводу шага при rc ≠ 0, см. ниже). Они идут **в дереве серии** (shared — основное, worktree — своё),
**под замками `resources`**, по явной команде человека. Вердикт шага: rc 0 — `PASS`; `inconclusive_rc`, таймаут и
«не удалось запустить» — `INCONCLUSIVE` (проверка не состоялась, дефекта не нашли); иначе `FAIL`.
**Различать «устройство/сеть недоступны» и «дефект» надо в самой проверяемой команде** — разными кодами возврата
(например, 2 = окружение, 1 = провал проверки) и `inconclusive_rc: 2`: команда, которая в обоих случаях возвращает 1,
даёт ложный `FAIL` (полевой разбор 20.11.2026: два «провала» были сетью и заблокированным экраном). Когда команду
не поменять, есть запасной путь: `inconclusive_match` — regex, который проверяется по выводу (stdout+stderr) **только
при rc ≠ 0**; совпадение даёт `INCONCLUSIVE` с причиной в результате, `PASS` не рождает никогда, а текст сообщений
команды — хрупкая опора (сменилась формулировка — шаг снова `FAIL`: безопасный отказ). Разбор JSON-вывода команды
(`ok:false`, коды причин) инструмент не делает намеренно: это формат конкретного проекта — его место в команде проекта. Итог серии:
любой `FAIL` → `FAIL`, иначе любой `INCONCLUSIVE` → `INCONCLUSIVE`, иначе `PASS`; шаги идут все (картина целиком, без
остановки на первом провале). Код выхода **0/1/2** = PASS/FAIL/INCONCLUSIVE; `2` же — «приёмка не настроена»,
«живая серия (lock занят)», «ресурс занят» (как `gates` на пустых шагах: «проверить нельзя» не путается с провалом).
Итог (вердикт, шаги, rc, время, HEAD, phase на тот момент) — в `state.json["acceptance"]` и в `status` (с пометкой
«УСТАРЕЛА», если HEAD с тех пор изменился); строка `ACCEPT-RESULT:` — для скриптов. **Вывод шагов в state не
пишется** (бывают секреты), он только в терминале.

Чего `accept` НЕ делает намеренно: не меняет `phase` (`done` остаётся прежним: решение — `set-verdict`/`merge`, за
человеком), не запускается сам по завершении серии (запускать ли код на оборудовании — решение человека) и не
гейтит `done`. Порядок после серии: `duo audit --task X` (нарушения границ) → `duo accept --task X` →
`commit-by-plan`.

Прогресс исполнителя: строки консоли — `· [мм:сс #N] Инструмент(аргументы)`: время от начала вызова модели и
порядковый номер действия в этом вызове; в логе старта solo — `модель: haiku → glm-5.3-flash` (во что алиас
отображается в профиле CLI; секреты `settings.json` в лог не попадают).

## Модели по ролям (glm-5.4 / 5.3 / 5.3-flash)

Ключи `models`, `effort`, `model_expect` в `config.json` (проект переопределяет в `.duo/config.json`; словари сливаются
по ключам). Значения — **алиасы профиля CLI** (`ANTHROPIC_DEFAULT_<АЛИАС>_MODEL` в `<claude_config_dir>/settings.json`):
`opus` = сильнейшая модель стенда, `sonnet` = средняя, `haiku` = дешёвая.

| роль | ключ | по умолчанию | комментарий |
|---|---|---|---|
| исполнитель | `models.executor` | `sonnet` (glm-5.3) | одна сессия на серию → модель закрепляется в `state.executor_model` |
| ревьюер (участник дуэта, проверяющий pair) | `models.reviewer` | `opus` (glm-5.4) | `feynman2`, `torvalds2`, `meadows2` |
| ревьюер-исключение | `models.<имя персоны>` | `socrates2` → `sonnet` | перекрывает `models.reviewer` для этой персоны |
| председатель, эскалация | `models.chairman` | `sonnet` | свод и триаж |
| solo | `solo.model` | `haiku` (glm-5.3-flash) | `models.executor` на solo НЕ влияет |
| запас | `model` | `sonnet` | роль без записи в `models` |
| рассуждение | `effort.<алиас>` | `opus: high` | `--effort` только для алиасов с записью; `low/medium/high/xhigh/max`. На high glm-5.4 «думает» 100+ тыс. знаков даже над 20-строчным планом (синтетика 25.11: 114 тыс. знаков, 9 мин, $1.25); medium — ≈ 3 тыс., ≈ 30 с, ≈ $0.16 при тех же найденных дефектах (по одному замеру, не калибровка) |
| лимит вывода ревьюеров | `claude_env_plan.CLAUDE_CODE_MAX_OUTPUT_TOKENS` | `64000` | только `mode=plan` (ревьюеры, председатель); дефолт claude CLI 32000 токенов общий на рассуждения и текст — упирались 6 из 9 «неполных отчётов» полевой волны 1. Исполнителя не касается (`claude_env_full`) |
| ожидания | `model_expect.<алиас>` | `opus: glm-5.4`, `sonnet: glm-5.3`, `haiku: glm-5.3-flash` | сверка с профилем стенда: предупреждение, не отказ |

- **Закрепление исполнителя:** первый запуск пишет `state.executor_model` (из `--executor-model ALIAS`, иначе из
  `models.executor`/`solo.model`); смена конфига, профиля и флагов на идущую серию не действует, конфликтующий
  `--executor-model` — отказ. `rework` без `--keep-session` открывает новую сессию и освобождает выбор. Серия,
  начатая до этой правки (есть сессия, нет пина), остаётся на алиасе `opus` (solo — на `solo.model`).
- **Где видно:** журнал запуска — строка `МОДЕЛИ: исполнитель: … ; ревьюер …`; `duo status` — строка `модели:`
  (и ключ `models` в `--json`); `duo selftest` — те же строки + пинг каждой различной модели.
- **Расхождение стендов:** NVIDIA и AMD обновляют профиль CLI отдельно; одинаковый `config.json` на старом профиле
  даёт ролям другие модели (например, `sonnet → glm-5.3-flash` вместо `glm-5.3`: исполнитель станет флэшем). Журнал и
  `selftest` скажут «ВНИМАНИЕ: профиль моделей отличается от ожидаемого — алиас … → …, ожидалось …»; лечится правкой
  профиля стенда (три строки `ANTHROPIC_DEFAULT_*_MODEL`), а не конфига.
- **Таймауты:** `reviewer_sec` = 900 — единый idle-лимит ревьюеров и единственного проверяющего pair: 5.4 на высоком
  effort молчит между событиями потока дольше 5.3; транспорт ревьюеров по умолчанию без повторов, поэтому слишком
  короткий лимит = лишний `halt`.

## Параллельные серии (2+ одновременно): `--worktree`

Одна серия — одно рабочее дерево. Две серии в ОДНОМ дереве убивают друг друга (GitGuard одной откатывает
правки и удаляет «чужие» новые файлы другой, смена ветки `duo/<task>` идёт под ногами). Поэтому параллель
— только через **worktree**: у серии своя папка `.worktrees/<task>` и ветка `duo/<task>`, артефакты по-прежнему
в `pipeline/<task>/` основного дерева (симлинк), GitGuard смотрит только своё дерево.

```bash
# терминалы/вызовы claude-glm из IDE — по одному на серию:
duo init --task a --mode pair --worktree
duo run --task a                 # план → impl_pending
duo run --task b --mode pair --worktree
duo claims                       # кто какие файлы занимает
duo run --task a --continue      # имплементация (занимает зону)
duo commit-by-plan --task a --yes # коммиты в ветку duo/a (в worktree)
duo merge --task a --dry-run     # что войдёт, будут ли конфликты
duo merge --task a               # влить duo/a → текущая ветка основного дерева
```

**Как предотвращаются коллизии (не магия, а три слоя):**

1. **Зона записи (`## files_touch`).** В worktree-серии исполнитель обязан закончить план секцией
   `## files_touch` — список путей (в бэктиках; glob и каталоги `dir/` допустимы), которые имплементация
   изменит/создаст/удалит. Секция — часть плана, ревьюер читает её вместе с планом (отдельной проверки зоны нет).
   Оркестратор пишет в лог `ЗОНА: plan_vN.md заявляет K путей` при приёмке плана (или предупреждает, что секции нет).
2. **Claim-gate при старте имплементации.** Перед ПЕРВЫМ запуском кода оркестратор (под `repo_lock`, атомарно)
   сверяет зону серии с зонами других worktree-серий, которые ещё не слиты. Зона держателя = заявленная ∪
   фактически изменённая в его worktree. Пересечение → серия остаётся в `impl_pending`, в `orchestrator.log`
   `БЛОК: … a (phase=impl): api/b.py ⇄ api/*.py`; исполнитель не вызывался, ничего не изменено. Нет секции
   `files_touch` и есть держатели → тоже блок (проверить нечем). Выходы: дождаться и `merge --task <держатель>`;
   `claims --task <держатель> --drop` (серия брошена); дописать зону в план; `run --task X --continue --ignore-claims`
   (на свой риск — конфликт при слиянии). Общие «горячие» файлы (напр. `doc/TODO.md`) выводятся из проверки
   в `config.json` → `parallel.shared_ok`.
3. **Слияние с проверкой.** `merge` сначала делает `git merge-tree --write-tree` (конфликты видны ДО касания
   дерева; их разрешают в worktree серии: `git -C .worktrees/<task> merge <ветка-цели>`), затем `merge --no-ff`;
   после слияния зона отпускается (параллельные серии больше не блокируются), worktree удаляется (ветка остаётся).
   Перед первой имплементацией база worktree подтягивается к HEAD основного дерева (fast-forward, только если в
   worktree ещё ничего нет; `parallel.sync_base_at_impl`), поэтому серия, стартовавшая после слияния соседа,
   уже видит его код. **Дифф имплементации и его ревью считаются от НОВОЙ базы** (лог: `БАЗА: worktree подтянут
   … план составлен на прежней базе`): коммиты, попавшие в основное дерево между планом и кодом, в дифф серии
   не входят и не должны — «дифф серии ⊆ files_touch» остаётся верным, а полный дифф ветки с момента старта
   плана — нет.
   **`merge` льёт в ту ветку, на которую указывает HEAD основного дерева.** Если там идёт ДРУГАЯ серия
   (`duo/<другая>`, не `done` или с занятым lock — типичный случай: shared-серия параллельно worktree-серии),
   слияние легло бы в её ветку и рабочее дерево посреди работы (она увидит чужой код, её ревью получит чужую
   базу) — `merge` (и `--dry-run`) **отказывает** с инструкцией: дождаться приёмки той серии
   (`duo wait --task <та>`) либо переключить основное дерево на целевую ветку (`git switch <основная>`);
   `--force` — на свой риск. Для принятой серии или ветки с префиксом серий без состояния — только ВНИМАНИЕ.
   Перед любым `merge`: `git branch --show-current` в основном дереве — это должна быть целевая ветка.

Выход имплементации за заявленную зону не блокируется (код уже написан), но попадает в `orchestrator.log`
(`ЗОНА: изменены файлы вне …`), в промпт ревьюеров кода и — если пересекается с зоной другой серии — в
уведомление.

**Две shared-серии в одном дереве запрещены:** `run` без `--worktree` при живой другой shared-серии отвечает
`ОТКАЗ` (проверка по занятому `.lock`; пара solo+solo допустима). Обойти осознанно: `--allow-shared-parallel`.

**Что НЕ защищено (важно):**

- Общие ресурсы вне git: сервисы проекта (какой не перезапускать — задаёт
  `executor_worktree_note` в `.duo/config.json`), GPU,
  каталоги из `git.worktree_links` (`data/`, `models/`, `node_modules` — симлинки
  из основного дерева, запись в них идёт в ОБЩИЕ данные), общая
  БД и очереди. Серии, которые тестируют на живом сервисе/GPU/боевой базе, параллелить нельзя.
- В worktree попадает только ЗАКОММИЧЕННОЕ: незакоммиченные правки основного дерева серия не видит (а merge
  ждёт чистый worktree серии — коммит через `commit-by-plan`).
- Зона — заявление исполнителя: слишком узкая зона пропустит конфликтную серию (конфликт всплывёт на `merge`
  как `КОНФЛИКТЫ`, дерево человека при этом не тронуто), слишком широкая — заблокирует соседей без нужды.
  Семантические конфликты (код сливается чисто, но не работает вместе) ловит только ваша приёмка после слияния.
- Серия изоляции `shared` и серия `worktree` друг друга не блокируют — shared-правки в основном дереве
  не проверяются claim-gate (остаётся обычный `git merge`).
- Изоляция серии не меняется после первого запуска (`ОТКАЗ … сменить нельзя`); начни новую серию.
- **Файлы, которые проект генерирует вне git** (напр. `*.csproj`/`*.sln` Unity, `node_modules`, сборочные
  артефакты), в worktree **отсутствуют**: компиляционная проверка кода там невозможна (в shared-серии она
  работает). Ревьюер плана честно не даст «обойти» это копированием из основного дерева (скомпилировался бы
  чужой код — ложный PASS). Если DoD требует «код компилируется» — запускайте серию в shared, либо
  планируйте результат INCONCLUSIVE (статическая проверка + ревью), либо дайте проекту генерацию этих файлов
  в `gates` вне дерева. Инструмент здесь ничего не «чинит»: это свойство среды.

Сделать worktree умолчанием для всех новых серий: `.duo/config.json` проекта (или
`config.json` инструмента) → `git.isolation: "worktree"` (флаг
`--worktree` тогда не нужен; серии `shared`, уже запущенные раньше, продолжат как shared благодаря пину).
Пока умолчание — `shared` (прежнее поведение).

## Разовое дуо-ревью произвольного артефакта (консилиум)

```bash
duo review --task <name> \
  --artifact pipeline/<name>/decision_briefing.md --phase custom
# отчёт: pipeline/<name>/rev{NNN}_custom.md; вердикт в последней строке
```

Ручной вердикт (пин, вывод из needs_human): `set-verdict --task <name>
--verdict ACCEPT|REVISE --note "..."` — семантика по фазам и команды `rework`/`hold`/`release`
см. раздел «Вмешательство человека» ниже.

**Контейнер ревью** (`--task` с одними `rev*_custom.md`, без `plan_v*.md`): после
`init` он висит в `phase=plan` — это штатно, сторож тревоги не даёт. Закрыть:
`set-verdict --task <name> --verdict ACCEPT --note "..."` → `phase=done` (с 10.10.2026;
раньше ACCEPT вёл в `impl_pending` и сторож запускал исполнителя на несуществующий
план). Контейнеру можно просто дать повисеть, `review` его не требует закрывать.

**Ловушка отката (инцидент 11.10.2026):** пока идёт `review`, оркестратор сравнивает НЕЗАКОММИЧЕННЫЕ новые файлы репозитория до/после каждого шага дуэта и **удаляет всё, что сочтёт созданным надсмотрщиком**
вне зон записи (`ОТКАТ: удалены файлы…` в `orchestrator.log`) — в том числе ваши рабочие скрипты и каталоги результатов, созданные в это время. Правило: во время `review` не создавать в репозитории
новых файлов (писать во `/tmp` и переносить после строки `вердикт …` в логе) либо сначала коммитить. Запущенные до отката процессы продолжают жить, но теряют каталог вывода.

## Вмешательство человека: set-verdict, rework, hold (pipework2, 14.10.2026)

**Ручную правку `state.json` больше не применять** (так терялся state целиком, забывался
`executor_session`, гонялись холостые ревью-раунды). `set-verdict`, `rework` берут `.lock`
и **отказывают, пока серия жива** (подсказка `ps aux | rg duo_pipeline`); `hold`/`release`
`.lock` не берут — они нужны именно при живом оркестраторе.

**`set-verdict --task X --verdict ACCEPT|REVISE [--phase plan|impl] --note "..."`**

| phase серии | ACCEPT | REVISE |
|---|---|---|
| `needs_human` (эскалация, лимит итераций, «артефакт ревью не найден») | из plan → `impl_pending`; из impl → `done`; старый `escalation.md` архивируется в `escalation_<ts>.md` | фаза возвращается (`plan`/`impl`), ставится маркер `rework` по **последнему** `rev*_<фаза>.md`; `run` первым шагом зовёт исполнителя (не ревьюеров); сессия исполнителя сбрасывается |
| `plan` (не контейнер) | → `impl_pending` | только запись вердикта (подсказка про `rework`) |
| `plan` (контейнер: только `rev*_custom.md`) | → `done` | только запись |
| прочие | только запись | только запись |

Фазу `needs_human` определяют по полю `escalated_phase` или по `stop_reason`; не опознана
(напр. `solo: исчерпан лимит`) — отказ с просьбой указать `--phase`.

**`rework --task X --phase plan|impl --review FILE [--keep-session] [--run] [--force]`** —
доработка артефакта по внешнему (экспертному) ревью:
регистрирует файл как `rev{NNN}_<фаза>.md` (допишет `VERDICT: REVISE`, если строки нет;
ревью с `VERDICT: ACCEPT` отклоняется), ставит `phase` + маркер `rework`, фиксирует
`iter_base`, чистит `executor_session` (`--keep-session` оставит), `--run` запускает `run`
detached. Отказы: живой процесс (`.lock`), `phase=done` без `--force`, нет плана/имплементации
(`plan_version`/`impl_version` = 0). Исполнитель первым вызовом получает **текст вашего
ревью** + (для impl) путь актуального диффа; новая версия `plan_v{N+1}` / `impl_report_v{N+1}`
идёт на обычное дуо-ревью.

Счётчики: лимит итераций и порог эскалации считаются **от момента вмешательства**
(`iter_base`), сырые `plan_iteration`/`impl_iteration` остаются монотонными. `max_plan_iterations`
поднимать за факт возврата не нужно. ACCEPT, выданные до вмешательства, новую эскалацию не гасят.

После `rework` до запуска `run` фаза = `plan`/`impl` без живого процесса — сторож может один
раз поднять «dead» (дедуп 1/час); `--run` это исключает. Перезапуск сторожа не нужен
(новых значений `phase` нет).

**[DEPRECATED с 30.10.2026 (`pipegates`): сторож больше не автопродолжает `impl_pending`, флаг ничего не выключает; команды работают как прежде и печатают предупреждение]** **`hold --task X` / `release --task X`** — флаг `hold_impl` (запрет автопродолжения
`impl_pending` сторожем) без правки `state.json`; остальные поля и heartbeat не трогаются.
Живой оркестратор флаг не затирает (при каждой записи state он подхватывает `hold_impl` с диска).
`release` при `impl_pending` → сторож продолжит в ближайший тик (~60 с).

**`run` при `phase=needs_human` без `--resume`/`--continue` ничего не делает** (пишет в лог, что делать).
Выходы: `set-verdict` / `rework` (решение эксперта) либо — для остановок с машинной записью `halt`
в state (pipework3) — `run --task X --resume [--add-budget USD] [--add-iterations N]`.

**Остановки (pipework3, 21.10.2026).** Любая ошибка оркестратора — чистая остановка: `phase=needs_human`,
`stop_reason`, `halt{kind,phase,resumable}` в state + строка `СТОП:` в `orchestrator.log` (раньше
`RuntimeError` убивал процесс молча с `phase=plan|impl`). Виды `halt.kind`:

| kind | когда | `--resume` |
|---|---|---|
| `limit` | исчерпан лимит итераций — **после** ревью+синтеза председателя, доработка по нему НЕ начата | нужно поднять лимит (`limits.max_*_iterations` или `--add-iterations N`); продолжает с доработки по последнему ревью (повторного ревью нет) |
| `budget` | `budget_usd` исчерпан (проверка — на границе итерации; начатое ревью доводится в пределах `budget_grace_usd`) | нужно поднять бюджет (`limits.budget_usd` или `--add-budget USD`) |
| `transport` | сбой вызова модели после `executor_api_retries`/`reviewer_retries` (idle-kill, claude без result); ревью: провайдер перегружен (`API Error: 529 … overloaded`, «timed out») и исчерпаны `limits.overload_retries` пауз (Н38) | да: прерванный шаг исполнителя повторяется **в той же сессии** с преамбулой «сверь состояние» |
| `crash` | внутренняя ошибка оркестратора (трейс — `orchestrator_bg.log`) | да (после починки) |
| `artifact_missing` | шаг исполнителя «завершился», но `plan_vN.md`/`impl_report_vN.md` не записан (оборванный ответ) | да: счётчик версии откатывается, шаг повторяется в той же сессии |
| `review_empty` | проверяющий вернул ACCEPT, не обратившись ни к одному инструменту, и повтор не помог (`review.empty_guard`) | да: ревью повторится; либо `set-verdict` после собственной проверки |
| `review_incomplete` (Н38) | ответ ревью раз за разом не умещается в лимит вывода модели (рассуждения съедают токены): повтор с пониженным effort тоже не помог. Вердикт НЕ выдан (подставного REVISE нет), потрачено уже учтено в `spent_usd` | да, но сначала поправить причину: `effort.opus: medium` в `.duo/config.json` либо больший `claude_env_plan.CLAUDE_CODE_MAX_OUTPUT_TOKENS`; надзор её не возобновляет (деньги) |
| `errata` | перенос эррат председателя в план не удался (пустой/частичный блок) | нет: дописать блок руками или `errata --task X --apply`, затем `set-verdict ACCEPT` |

`--resume` в отличие от `--continue` **не пересекает** паузу `impl_pending` (запуск имплементации — решение эксперта).
Число повторов транспорта/«дожимающих» ходов при ненаписанном артефакте — `limits.executor_api_retries`,
`executor_continue_retries`, `reviewer_retries` (config.json).

**Эрраты плана — конвенция.** При `review.plan_policy=triage` оркестратор **сам** дописывает блок
`## Эрраты к плану` председателя из принятого `revNNN_plan.md` в конец `plan_vN.md` (pipework3: дословно,
с маркером `<!-- duo:errata revNNN_plan.md sha256:… -->`, идемпотентно, при пустом/частичном блоке —
остановка `errata`, а не молчаливая порча). Статус/повтор: `errata --task X [--apply]`. Эксперт по-прежнему
может дописать СВОИ эрраты (раздел `## Эрраты…`, любой регистр, `#`–`######`, в **конце** файла). Оркестратор в impl-фазе сам
подмешивает его: исполнителю (`implement`/`revise_impl`: «перечитай план целиком», обязательная
таблица «эрраты → файл:строка/тест» в отчёте), ревьюерам и председателю (путь плана + чек-лист
«каждая эррата реализована, иначе блокер»). Нет раздела — промпты не меняются ни на байт.
Задание (`task.md`) в промптах больше не обрезается (раньше 4000/3000 симв.; предохранитель 60 000
с пометкой «обрезано»).

## Мониторинг

| что | где |
|---|---|
| события серии (фазы, вердикты) | `tail -f pipeline/<task>/orchestrator.log` |
| живая консоль исполнителя (каждая команда) | `tail -f pipeline/<task>/orchestrator_bg.log`. Если консоль пуста ≥120 с (Н24/Н40), печатается пульс `… жду ответ модели: без вывода N с, тишина потока K с (отсечка по тишине M с), рассуждений ≈T ток.` — отсчёт от **последней напечатанной строки**, а не от тишины потока: пока модель «думает», claude CLI шлёт `system/thinking_tokens` десятками в секунду, поток не молчит, а консоль пуста минутами (поле: 24 мин без единой строки); `рассуждений ≈T` — оценка токенов рассуждений текущего сообщения; возраст последнего вывода — в `status --task X` (строка «консоль…», JSON `process.console_age_sec`). **Признак жизни — занятый lock (`процесс: running`), а не свежесть `state.json`/консоли**: модель «думает» минутами без событий |
| состояние (phase, счётчики, $) | `pipeline/<task>/state.json` |
| сводка по всем сериям (+ процесс: running/dead/halted…, колонка `режим`: `pair/wt`, `duo/sh`, `—/—` у старых) | `duo status --all` |
| состояние одной серии для скрипта оператора | `duo status --task X --json` — **ровно один** JSON-объект (`phase`, `mode`, `isolation`, `budget`, `process`, `halt`, `claim`, `accepted_plan`, `review_transport`, полное `state`). Обычный `status --task X` печатает JSON состояния **и** текстовые строки подряд — `json.load` на нём падает («Extra data»); он для глаз |
| что исполнитель реально вызывал (Bash/Read/Write…), нарушения границ задания | `duo audit --task X [--json]` — по журналу сессии CLI, read-only; правила и ограничения — раздел «Серии на живом оборудовании». `status --task X` показывает технические запреты (`executor_deny`) и занятость ресурсов (JSON: `guard`) |
| зоны записи worktree-серий и их пересечения | `duo claims [--task X]` |
| ждать остановки/приёмки (для агента/скрипта) | `duo wait --task X` → `WAIT-RESULT: …`, код 0/10/11/12/13. У остановки печатается причина внутри вида: `halt=transport cause=quota reset=2026-11-25T13:39Z` (Н46) — «ждать до сброса», а не «сбой сети» |
| надзор (алерты, авто-возобновление, уведомления) | `systemd --user`: `duo-supervise.timer` (раз в 2 мин; без `--repo` — по реестру проектов) — см. `docs/CHEATSHEET-WATCHDOG-FAILSAFE.md`. Строка журнала `SUPERVISE: … \| уведомление: <итог>` — **итог доставки**: `принято демоном уведомлений` / `НЕ доставлено: <причина>` / `выключено (notify.desktop=false)` / `уже принято демоном при остановке (оркестратор)` / `dry-run`. Одна строка `notice`/`alert` без этого итога доставкой не считается. Уведомление о `done`/`impl_pending` — **одно на событие** (ключ — отпечаток «фаза + потрачено + версии плана/кода», а не heartbeat state: повторные `accept`/`hold` после завершения новых уведомлений не рождают; доработка с новыми тратами — рождает). Сообщения надзора — в журнале systemd, а не в `orchestrator.log` |
| **сторож** — ждать события после запуска (обязательно: иначе простой часами; см. «СТОРОЖА» выше) | сразу после `run`/`run --continue` — `duo wait --task X --timeout 3600 --quiet` в фоне (блок «СТОРОЖ» печатается самим `run`); агенту — `notify_on_output` по `WAIT-RESULT`; `nohup … > файл &` без чтения файла молчит. Вернувшись в сессию — `duo status --task X`: строка `ЖДЁТ ВАС N мин` / `ЗАВЕРШЕНА N мин назад`. Второй `run --continue` «для надёжности» не нужен: отказ `.lock` означает, что первый запуск удался |

Старый `watchdog.sh` (живой bash-цикл) и `watchdog_failsafe.sh` **выведены** (pipework3): штатный надзор —
`duo_pipeline.py supervise` (источник истины — state + `flock` на `.lock`, не `ps`/`pgrep`). Автопродолжение
`impl_pending` сторожем **убрано**: запуск имплементации — решение эксперта (`run --task X --continue`).

## Частые грабли (зафиксировано инцидентами)

- **Параллельные серии**: GitGuard больше не откатывает tracked-файлы
  чужих каталогов `pipeline/*` (калечил живые state/solo_report). НЕ
  коммитить mutable-файлы ЖИВОЙ серии (state.json, solo_report,
  transcripts) — дождись `done`. Две серии с кодом — только в своих worktree
  (`--worktree`, раздел «Параллельные серии»); второй `run` в общем дереве при живой shared-серии теперь
  отбивается `ОТКАЗ`, а не молча убивает первую.
- **pgrep/pkill в песочнице**: паттерн совпадает с командной строкой
  самой песочницы → мнимые процессы/самоубийство. Фильтруй
  `grep -v "/bin/bash"` или убивай по точному PID.
- `needs_human` = точка входа человека: `set-verdict` / `rework` (см. раздел выше);
  `run` в этом состоянии ничего не делает. Не править `state.json` руками.
- Бюджет серии: `limits.budget_usd` (общий на серию, сейчас $220 + `budget_grace_usd` $15 на доведение ревью;
  добавка конкретной серии — `--add-budget`).

## Восстановление серии и защиты от типовых отказов (полевая проверка 16.11.2026)

Боевой прогон на постороннем проекте (серии pair/shared и duo/worktree) вскрыл шесть дыр; ниже — что
инструмент делает теперь и что остаётся человеку. **Руками удалять `pipeline/<task>/` и править
`state.json` по-прежнему нельзя** — для чистого листа есть `reset`.

| ситуация | что делает инструмент | что делать человеку |
|---|---|---|
| Серия отказала на старте / нужен чистый лист | `duo reset --task X [--dry-run] [--yes] [--force]`: всё содержимое каталога серии (state, планы, ревью, логи, транскрипты) **не удаляется, а переезжает** в `pipeline/X/_reset_<метка>/`; **`task.md` не трогается** и это печатается; снимаются worktree `.worktrees/X` и ветка `duo/X`. Отказ (без `--force`): `phase=done`, грязный worktree, коммиты ветки, не слитые в HEAD. Живую серию (lock занят) не трогает даже с `--force`. Бюджет после reset считается заново (потраченное видно в `_reset_*/state.json`) | `duo reset --task X --dry-run` → `--yes`; затем `duo init --task X [--mode … --worktree]` (прежние пины печатаются) и `run` |
| worktree-серия, а `pipeline/<task>/` закоммичен в HEAD | `init --worktree` и `run` отказывают **до** создания worktree и ветки (раньше узнавали на provisioning, оставляя ветку-сироту и устаревший пин базы) | другое имя серии, либо `git rm -r --cached pipeline/<task>` + коммит (решение человека), либо серия без `--worktree`. **task.md worktree-серии не коммитить до `merge`** |
| Сбой provisioning при создании worktree | откат: worktree снят, ветка `duo/X` удалена (только если создана этим же запуском — наработки прошлых попыток не трогаются), пин `worktree_base` снят; повтор `run` стартует с **текущего** HEAD. Если пин устарел, а ни worktree, ни ветки нет — в логе строка `БАЗА: пин worktree_base … устарел` | починить причину (текст отказа в логе) и повторить `run` |
| `task.md` пропал, `init` записал шаблон | `init` печатает ВНИМАНИЕ (следы серии есть, задания нет); `run` на нетронутом шаблоне или пустом файле отказывает до любых побочных эффектов | восстановить задание из git/бэкапа; не запускать на шаблоне |
| Незакоммиченная серия, нужны гейты | `gates` печатает ВНИМАНИЕ `ref=HEAD НЕ содержит N незакоммиченных изменений — проверяется бейзлайн` (в начале, в финальной строке и в `summary.txt` строкой `WARN`). `--dirty` накладывает правки дерева серии (изменённые, новые, удалённые файлы; без `pipeline/`); для worktree-серии — правки из её worktree. `--extra` принимает **каталоги** (файлы под git: tracked + untracked, без игнорируемых) и берёт файлы из **основного** дерева; абсолютный путь допустим, если он внутри корня проекта (вне корня — отказ). Файлы, покрытые `--extra` (shared-серия), в счёт ВНИМАНИЯ не входят; удалённый файл `--extra` не накладывает, а у worktree-серии покрытия нет вовсе (другое дерево) — ВНИМАНИЕ остаётся, нужен `--dirty` | `duo gates --task X --dirty` либо сначала `commit-by-plan`, потом `gates` |
| `commit-by-plan` и заранее написанный `task.md` другой серии | артефакты **других серий** (каталог `pipeline/<иная>/` с `task.md` или `state.json`) не попадают в «файлы вне групп», не блокируют `--yes` и не коммитятся этой командой; печатаются отдельной строкой. Прочие файлы под `pipeline/` — по-прежнему uncovered | не коммитить чужой task.md «чтобы разблокировать»: для worktree-серии это ломает её старт |
| Приёмка серии: что делать **до** `commit-by-plan` | `commit-by-plan --dry-run` (read-only) печатает «предсказание для `--yes`: пройдёт / ОТКАЖЕТ — причины» по тем же правилам, что и сам `--yes`: uncovered, overlap, пустые группы, предупреждения парсера, **чужой staging**. Реальный отказ по staging подсказывает `git -C <дерево серии> reset` (сбрасывает только индекс, правки в файлах целы) | **не `git add` в дереве серии** до `commit-by-plan`: гейтам индекс не нужен (`duo gates --dirty`). Порядок: `commit-by-plan --dry-run` → `--yes` → `gates` → `merge` |
| Python-проект: `.pyc` от прогона тестов | `duo setup` дописывает в `.gitignore` блок «Python-мусор прогонов» (`__pycache__/`, `*.py[cod]`), если под git есть `*.py` и мусор не игнорируется; `init` предупреждает, если нет (проект подключён давно/вручную). Без игнора `.pyc` попадают в предупреждение «вне files_touch» ревьюеру и в uncovered `--yes` | добавить `__pycache__/` в `.gitignore` и закоммитить ДО серии (для worktree — до `run`: база берётся из HEAD) |
| Момент решения о запуске кода (`impl_pending`) | `status --task X` печатает «принято: план vN принят ревью revNNN; эрраты: K п. (строк списка с вложенными: L); зона записи: M путей (…); потрачено $…» и подсказку `run --continue`; та же сводка печатается самой командой `run --task X --continue` перед запуском | сверить сводку с прочитанным планом: число эррат и зона — из state, расхождение с `plan_vN.md` — вопрос к инструменту. K — верхнеуровневые пункты блока, L (показывается, только если больше K) — все строки списка с подпунктами (Н34: раньше печаталось одно L — «21 пунктов» при 9 эрратах) |
| Скрипты исполнителя в каталоге артефактов worktree-серии (симуляции, замеры) | в worktree `pipeline/<task>` — **симлинк** на артефакты основного дерева (они живут в одном месте). Скрипт оттуда, определяющий корень проекта через `Path(__file__).resolve()`/`realpath`, уходит в основное дерево со **старым** кодом (полевой прогон 17.11.2026: `AttributeError` на новой константе, потерян ход модели). Исполнитель worktree-серии (pair/duo/solo) получает в промпте предупреждение; корень надо брать от cwd (запуск из корня worktree) или `Path(__file__).absolute()` | при странной ошибке «старого кода» в скрипте из `pipeline/<task>/` — первым делом проверить, какое дерево он реально грузит |
| `commit-by-plan` вернул rc=1, хотя коммиты прошли | rc=1 — **любой хвост**: пропущенные/пустые/неудавшиеся группы, `uncovered` (файлы вне плана — чаще всего грязь дерева ДО задачи), overlap, предупреждения парсера. Группы-артефакты серии («коммитятся отдельно») в условие **не входят**. Финал печатает `ИТОГ:` (прошли коммиты групп или нет, из-за чего код 1) и машинную строку `COMMIT-RESULT: committed=… skipped=… failed=… empty=… uncovered=… overlaps=… warnings=… rc=…` (`--dry-run`: `COMMIT-RESULT: dry-run yes=pass\|refuse …`; при явном `ОТКАЗ --yes` и чужом staging строки нет — отказ случился ДО коммитов). Код возврата не менялся | скрипты оператора читают `COMMIT-RESULT`, не угадывают по rc; `failed>0` — настоящий сбой коммита, остальное — хвосты (закоммитить вручную или дополнить `## commit_plan`) |

## Боевая проверка pair + worktree (29.10.2026: серия A pair ∥ серия B duo) — что выучено

Две серии одновременно, обе `--worktree`; зоны записи — 2 и 6 путей, непересекающиеся. серия A (pair,
~30 строк кода + 16 тестов): план 11:00→11:12 (исполнитель 5 мин + `feynman2` 6 мин, 3 эрраты), код 11:19→11:42
(23 мин) + ревью `torvalds2` 7 мин, ACCEPT с 1-го захода, **итого ≈ 50 мин и $5,2**; `commit-by-plan` → `merge --dry-run`
(конфликтов нет) → `merge --yes` → worktree снят, ветка `duo/<A>` осталась. Серия B (duo): план 11:02→11:29
(27 мин, ACCEPT с 1-го раунда, 6 эррат). Что подтвердилось и что нет:

**Работает как описано**
- Claim-gate: `claims` показывает зону держателя; серия `done` держит зону **до `merge`** (отпускается строкой
  `MERGE … зона записи отпущена`), так что слитый/брошенный результат не оставлять висеть.
- `merge` на «грязном» основном дереве (чужой незакоммиченный WIP владельца в файлах, которых серия не касается)
  проходит, если файлы не пересекаются с диффом серии. `merge --dry-run` предсказал чистое слияние.
- `commit-by-plan --task X --yes` в worktree: симлинки `models`, `node_modules`, `pipeline/<task>` не коммитятся.
- Параллельные CPU-тяжёлые измерения соседней серии B (`taskset -c 16-27`, nice 10) работе pair-серии не мешали.
- `wait --task X --timeout N --quiet` печатает `WAIT-RESULT: timeout|done …`; `timeout` — это ваш потолок, не сбой серии.

   **Несколько путей в ячейке «файлы (glob)» (Н43):** каждый путь/glob — в СВОИХ бэктиках, через запятую: `` `a.sh`, `b.sh` ``.
   Запись `` `a.sh b.sh` `` (один спан с пробелом) — это ОДИН glob с пробелом: он ничего не находит, группа выглядит пустой, а
   `--yes` отказывает по `uncovered`. Парсер спан не режет (пробел в пути законен), но при пустой группе с пробелом в glob
   печатает «подсказка: в glob есть пробел …». Пример формата — в `task.md`, если от исполнителя нужен `commit_plan` (поле: с примером
   формат прошёл с первого раза).
8. **Исполнитель долгой серии с ssh-стендом:** (а) не написал `impl_report` с первого прохода — понадобились два «дожимающих»

## Ночная цепочка серий (runbook-паттерн, выучен 05–06.10)

Автономная цепочка «серия → серия → …» без человека на ночь:
`init --task X` → `run` → (по событию завершения) гейты ruff+pytest unit →
`commit-by-plan --task X` (подтверждения: `printf 'y\ny\n...' |`) → артефакты →
merge --no-ff в feature-ветку → push → следующая серия. Ключевые правила:
- сторож следит за `pipeline/<task>/state.json` (phase=done / stop_reason), НЕ за
  `tail -1` лога (монитор по логу проспал финал pipev3);
- при СТОПе по бюджету/лимиту итераций: `run --task X --resume --add-budget USD` /
  `--add-iterations N` (правка state.json не нужна);
- `printf 'y\n...' |` перед commit-by-plan (без stdin все группы n/EOF);
- опечатки в путях редиректа ломают argparse молча — копировать команды целиком.

## Уборка pipeline/ (серия pipearchive, 01.11.2026): команда `archive`

Завершённые серии (`merge` прошёл + карантин **14 дней**) убираются из `pipeline/`
**только** командой оркестратора `archive` — ручное `rm -r` запрещено (Правило 5
`pipeline/expert/pipeline_cleanup_plan_20261101.md` §11): без снимка и дайджеста
удаление невозможно, тяжёлые untracked тег в git не сохраняет.

Порядок (обязательный):

```bash
# 0) сводка: кто готов (возраст, карантин, дайджест, ссылки вне pipeline/)
duo archive --list
# 1) дайджест: заготовка с механической подстановкой (даты ветки, L1 task.md, размер);
#    поля-суждения (<заполнить>) заполняет ЧЕЛОВЕК, запись вставляется в pipeline/ARCHIVE-INDEX.md
duo archive --task X --print-digest-template
# 2) репетиция: печатает всё, что сделал бы, не меняя ни байта
duo archive --task X --dry-run [--archive-root ~/pipeline_archive/<дата>]
# 3) исполнение: допуск → снимок → верификация → удаление → ARCHIVED.txt
duo archive --task X --yes [--force-young] [--min-age-days 14]  # 0 = отключить карантин
# 4) правка указателей-на-серию в файлах проекта (напр. doc/TODO.md) на pipeline/ARCHIVE-INDEX.md#X
# 5) КОММИТ ЧЕЛОВЕКА (staged-удаления серии), напр. `chore(pipeline): archive X` → гейты
```

Что делает `archive --task X`: проверяет допуск (серия слита; возраст ≥ 14 дн, иначе
`--force-young`; нет живого worktree/занятого `.lock`; артефакты закоммичены; дайджест
`### X` в `pipeline/ARCHIVE-INDEX.md` **без** `<заполнить>`; нет ссылок `pipeline/X`
вне `pipeline/` кроме файлов из `archive.guard_exempt_files` + каталогов
`archive.guard_skip_dirs` проектного конфига) → снимок всего каталога
(`tar.zst`, без `transcripts/`, `logs/`, `state.json`, `orchestrator*.log`, `.lock`,
`*.pid`, `untracked_impl_v*.txt`; симлинки не включаются) в
`~/pipeline_archive/<ГГГГММДД>/series/X.tar.zst` + строка в `MANIFEST.tsv` (дозапись)
→ верификация (`zstd -t`, sha256, сверка с свежим обходом дерева; любое расхождение —
**откат без удаления**) → `git rm -r` + удаление остатка → имя в
`pipeline/archive/ARCHIVED.txt` (сортированно, без дублей).

Что НЕ делает: не коммитит и не мержит (коммит делает человек), не переключает ветки,
ветку `duo/X` сохраняет, `transcripts/`/`logs/` не архивирует — удаляет (решение
владельца §11-4). Отказы: нет `zstd`, мало места в `--archive-root` (оценка по
raw_bytes), неуникальное имя снимка. Восстановление: распаковать
`~/pipeline_archive/<дата>/series/X.tar.zst` (пути `pipeline/X/…` уже внутри) или
`git checkout pipeline-archive-<дата> -- pipeline/X` для tracked-части.
