# duo-пайплайн: запуск из любого проекта

Единый источник истины — репозиторий инструмента (`$DUO_HOME`: код, шпаргалки, персоны, этот
скилл). Найти его: `dirname "$(dirname "$(readlink -f "$(command -v duo)")")"`. В проект
инструмент НЕ копируется: проект хранит только `pipeline/<task>/` (артефакты серий) и
необязательный `.duo/config.json`.
Подробно: `$DUO_HOME/docs/CHEATSHEET-CONTROL.md` (управление) и
`$DUO_HOME/docs/PROJECT-SETUP.md` (подключение проекта, ключи конфига, несколько машин).

Команда `duo` доступна из любого каталога; корень проекта определяется сам:
`--repo PATH` > `$DUO_REPO` > git-корень текущего каталога (из `.worktrees/<task>` — основное
дерево). Всегда запускай `duo` из каталога нужного проекта либо передавай корень явно:
`duo --repo /путь/к/проекту run --task NAME` (`--repo` — глобальный флаг, ставится
ДО подкоманды; после неё argparse его не примет).

## СТОРОЖА — не пропусти конец фазы (читай до первого `run`)

Серия идёт в фоне, а конец фазы **тихий**: «план принят» (`impl_pending`) и «код принят» (`done`) никто не
объявит, пока ты не следишь; `impl_pending` сам не стартует. В полевых отчётах оператор не раз пропускал конец
фазы — серия стояла по 17–20 минут впустую.

- **Сразу после КАЖДОГО `duo run` / `duo run --continue`** (в ту же минуту, не «потом») запусти сторожа В ФОНЕ:
  `duo wait --task NAME --timeout 3600 --quiet` с `notify_on_output` по `WAIT-RESULT`. Итог:
  `WAIT-RESULT: done | impl_pending | halted | dead | idle | timeout` — на любой из них реагируй сразу
  (`impl_pending` → читай план и решай про `--continue`; `done` → `gates`/`audit`/`accept`; `halted`/`dead` → `status`).
- `nohup … > файл &` без чтения файла **молчит**: сторож, которого никто не читает, не сторож.
- Страховка — надзор (`duo-supervise.timer`): уведомление рабочего стола, если проект подключён (`duo projects`).
  Его след — не `orchestrator.log`, а `journalctl --user -u duo-supervise.service | grep SUPERVISE`.
- Потерял сторожа (рестарт сессии, обрыв ssh) или вернулся из паузы: `duo status --task NAME` — строки
  `ЖДЁТ ВАС N мин` / `ЗАВЕРШЕНА N мин назад`.

## Режимы

| режим | кто | стадии | вызовов модели на итерацию ревью | когда брать |
|---|---|---|---|---|
| `solo` (`--solo`) | один исполнитель на дешёвой модели (`solo.model` = `haiku` → `glm-5.3-flash`) | только код, без плана и ревью | — | артефактные и измерительные задачи, дорогое планирование избыточно |
| `pair` (`--mode pair`) | исполнитель + один проверяющий (`feynman2` на план, `torvalds2` на код) | план → код | 1 | средний риск: 1–3 файла, чёткие критерии, воспроизводимая проверка |
| `duo` (по умолчанию) | исполнитель + дуэт + председатель | план → код | 7 | схема данных, конвейеры, пре-регистрация, риск тихой подмены результата |

Режим и изоляция пинуются в `state.json` при первом запуске; `--continue`/`--resume`/надзор
берут их оттуда. Ориентиры цены: pair ≈ $5–15 на небольшую серию, duo ≈ $10 за итерацию.

## Модели по ролям

Роли получают модели **по алиасам профиля CLI** (`~/.claude-glm/settings.json`, `ANTHROPIC_DEFAULT_<АЛИАС>_MODEL`):
`opus` — сильнейшая модель стенда (сейчас `glm-5.4`), `sonnet` — средняя (`glm-5.3`), `haiku` — дешёвая
(`glm-5.3-flash`). Назначение — ключи `models`/`effort` в `config.json` (проект переопределяет в `.duo/config.json`):

| роль | алиас → модель | effort | почему |
|---|---|---|---|
| ревьюеры кода и плана: `feynman2`, `torvalds2`, `meadows2` | `opus` → **glm-5.4** | `high` | проверка — самое дорогое место ошибки: ловить баги, тихие подмены, гонки, архитектуру; 5.4 сильнее именно в длинном рассуждении над большим контекстом (1M) |
| `socrates2` (диалектик плана) | `sonnet` → glm-5.3 | — | спор о необходимости механизмов не требует глубины 5.4; другая модель = разнообразие дуэта |
| председатель дуэта, эскалация | `sonnet` → glm-5.3 | — | свод трёх-четырёх текстов и триаж; другая модель, чем у части ревьюеров |
| исполнитель | `sonnet` → glm-5.3 | — | откалиброван на ней; **одна сессия на серию**, поэтому модель закрепляется в `state.executor_model` |
| `solo` | `haiku` → glm-5.3-flash | — | дешёвые артефактные серии (≈1/40 цены топ-моделей) |

Правила:
- **Модель исполнителя — на серию:** `duo run --task NAME --executor-model opus` при первом запуске (тяжёлая
  архитектурная правка, сложный рефакторинг); после старта смена отказом (`rework` без `--keep-session` начинает
  новую сессию и освобождает выбор). Серия, начатая до этой правки, остаётся на прежнем алиасе.
- **`effort` задан по алиасу** (`effort.opus = high`), а не по роли: `max` — точечно (большой дифф, спорная
  архитектура) через `.duo/config.json`. У glm-5.4 дефолт CLI — `max`: на нём она заметно медленнее 5.3 и подолгу
  «думает молча» — поэтому `timeouts.reviewer_sec` = 900 (это секунды ТИШИНЫ, не общее время).
- **Профиль — часть стенда, не репозитория.** NVIDIA и AMD обновляют профили отдельно, а `config.json` один. `model_expect`
  хранит ожидаемое (`opus → glm-5.4` …); расхождение — строка «ВНИМАНИЕ: профиль моделей отличается» в журнале запуска и
  в `duo selftest` (не отказ). Строка «МОДЕЛИ: …» в журнале каждого запуска и «модели:» в `duo status` показывают, кто
  на какой фактической модели.
- **glm-5.4 доступна только на подписке Coding Plan** (в API цена и доступ на момент записи не опубликованы): если
  модели нет на вашем тарифе, ревьюеры упадут транспортной ошибкой — `duo selftest` пингует КАЖДУЮ модель ролей и
  ловит это до серии. Временный откат — `models.reviewer: sonnet` в `.duo/config.json`.
- **Не откалибровано на живых сериях:** сроки/стоимость ревью на 5.4 и ценность `high` против `max` ещё не измерены —
  первая серия с 5.4-ревьюерами записывает их в отчёт (см. `docs/FIELD-TEST-BRIEF.md` §4.6).

## Подключение проекта (один раз)

```bash
cd /путь/к/проекту
duo setup            # .duo/config.json, строки в .gitignore, запись в реестр проектов
```

Проект без git: `duo setup` предложит `git init` (нужен хотя бы один коммит для worktree-серий).
В `.duo/config.json` задаются: `executor_env_hint` (окружение/команды тестов для исполнителя),
`executor_worktree_note`, `gates.steps` (гейты поставки в чистой копии), `git.worktree_links`
(какие тяжёлые каталоги линковать в worktree), `guard.never_revert`, `archive.*`.

## Рабочий цикл

```bash
duo init --task NAME --mode pair [--worktree]   # создаёт pipeline/NAME/{task.md,state.json}
                                                # (готовое задание: --task-file ФАЙЛ; режим solo: init без --mode)
# написать задание в pipeline/NAME/task.md (см. «Как писать задание»)
duo run --task NAME                             # стадия «план», detached
duo wait --task NAME --timeout 3600 --quiet     # СТОРОЖ, В ФОНЕ, сразу после run (см. блок выше); WAIT-RESULT: …
# прочитать plan_vN.md и revNNN_plan.md; если план годится:
duo run --task NAME --continue                  # стадия «код»
duo wait --task NAME --timeout 7200 --quiet     # снова сторож: конец «кода» тоже тихий
duo gates --task NAME [--dirty]                 # гейты в чистой копии (если настроены gates.steps);
                                                # серия не закоммичена → без --dirty проверится бейзлайн HEAD (будет ВНИМАНИЕ)
duo commit-by-plan --task NAME --dry-run        # read-only: «предсказание для --yes: пройдёт/ОТКАЖЕТ — причины»
duo commit-by-plan --task NAME --yes            # разложить коммиты по ## commit_plan отчёта
duo merge --task NAME --dry-run && duo merge --task NAME --yes   # только worktree-серии
```

`solo`: `duo init --task NAME`, затем `duo run --task NAME --solo` (план и ревью пропускаются;
итог — `solo_report.md`). `solo --worktree`: исполнитель по просьбе пайплайна пишет `impl_report_v1.md` с `## commit_plan`
(путь до `main`: `commit-by-plan` без `--version` берёт самый свежий отчёт → `gates` → `merge`; несколько путей в ячейке
«файлы» — каждый в своих бэктиках через запятую).
«Проверяющий вернул неполный отчёт» — не про формат: у каждой непринятой попытки в журнале есть класс (`output_limit`,
`transient`, `api_error`, `stub`, `format`); разбор и счётчики — `CHEATSHEET-CONTROL.md`, раздел «Восстановление серии и защиты от типовых отказов».
Состояние: `duo status --task NAME` / `duo status --all`; логи — `pipeline/NAME/orchestrator.log`.
Для скриптов — `duo status --task NAME --json` (ровно один JSON-объект); обычный вывод `--task` — JSON и текст подряд,
`json.load` на нём падает.
Чистый лист для серии, отказавшей на старте: `duo reset --task NAME --dry-run`, затем `--yes` (всё, кроме `task.md`,
переезжает в `_reset_<метка>/`; worktree и ветка снимаются, наработки защищены). **Никогда `rm -rf pipeline/NAME` и
правка `state.json`.** Worktree-серии: `pipeline/NAME/` (в т.ч. `task.md`) не коммитить до `merge`.
**Не `git add` в дереве серии до `commit-by-plan`** (для гейтов — `duo gates --dirty`); перед `--yes` — `--dry-run`.
Python-проект: `__pycache__/` должен быть в `.gitignore` и закоммичен ДО серии (`duo setup` это делает).
Остановки (`needs_human`): `duo run --task NAME --resume [--add-budget USD] [--add-iterations N]`
для машинных halt; решение эксперта — `duo set-verdict --task NAME --verdict ACCEPT|REVISE --note "…"`
или `duo rework --task NAME --phase plan|impl --review FILE --run`.
Все проекты и надзор: `duo projects`; тик надзора `duo supervise` (systemd-таймер по всем проектам; он сам
возобновляет «мёртвые» серии за счёт бюджета — перед включением на машине см. `$DUO_HOME/docs/CHEATSHEET-WATCHDOG-FAILSAFE.md`).

## CI и гейты: три контура, не путать

- **CI проекта** (напр. GitHub Actions) проверяет код ПРОЕКТА; тесты оркестратора он не
  исполняет (после этапа 2 они живут только в репозитории инструмента).
- **Гейты серии** `duo gates --task NAME` — локальное зеркало CI проекта в чистой копии;
  шаги — `gates.steps` в `.duo/config.json` проекта. Их потребитель — тот, кто принимает серию:
  ACCEPT ревьюера не значит, что гейты воспроизведены. Нет `gates.steps` — rc=2, гонять ruff/тесты
  проекта вручную в чистой копии.
- **CI инструмента** — `make check` в `$DUO_HOME` (ruff + pytest). Нужен
  только при правке самого оркестратора; серия проекта его не меняет. Красный здесь = риск для
  ВСЕХ проектов.

Подробности и правила синхронности: `$DUO_HOME/docs/CHEATSHEET-CONTROL.md`,
раздел «CI и гейты».

## Как писать задание (`task.md`)

Задание передаётся исполнителю ЦЕЛИКОМ. Хорошее задание содержит: контекст и цель; **жёсткие
границы записи** (какие пути менять, что не трогать, что не запускать — сеть, прод, перезапуск
сервисов); требования с точными интерфейсами (имена флагов, ключей, форматы); **критерии приёмки
как команды** с ожидаемым выводом (в отчёте исполнитель обязан привести фактический вывод,
а не пересказ); известные подводные камни. Для worktree-серий план обязан кончаться секцией
`## files_touch` (заголовок без номера), отчёт — таблицей `## commit_plan`.

## Правила и грабли

- **Не править `state.json`, `.lock`, `orchestrator*.log`, `transcripts/` руками** — только
  `set-verdict`/`rework`/`run --resume`. Они берут `.lock` и отказывают, пока серия жива.
- **Пока идёт ревью, не создавай новые файлы в репозитории проекта**: оркестратор удаляет всё, что
  сочтёт созданным надсмотрщиком (`ОТКАТ: удалены файлы…`). Свои заготовки — в `/tmp`, переноси после
  вердикта. Для pair/duo в shared-режиме то же относится к правке tracked-файлов.
- **Две серии с кодом в одном дереве запрещены** → параллельные серии только с `--worktree`.
  В worktree попадает только закоммиченное; общие ресурсы вне git (порты, GPU, БД) не изолированы.
- **Серия управляет живым оборудованием** (телефон, GPU, порт): «не делай X» в `task.md` — лишь текст, исполнитель
  идёт в bypass-режиме. В `.duo/config.json` проекта: `executor_deny` (технические запреты CLI), `resources`
  (машинный замок на ресурс; вторая серия получает отказ с именем держателя), `acceptance.steps`,
  `supervisor.auto_resume: false`. После серии: `duo audit --task NAME` (что исполнитель реально вызывал), затем
  `duo accept --task NAME` (живая приёмка; `phase` не меняет). Подробности и ограничения — раздел «Серии на живом
  оборудовании» в `$DUO_HOME/docs/CHEATSHEET-CONTROL.md`.
- **ACCEPT ≠ гейты воспроизведены**: ревьюер pair не перегоняет тесты, числа в отчёте — со слов
  исполнителя. Сам прогони `duo gates` либо ruff/тесты проекта в чистой копии. Ревью без цитат
  из дифа и без проверенных цифр — «вхолостую», приёмкой не считать.
- Коммит и merge — решение человека: `commit-by-plan --yes` — all-or-nothing, смотри сводку групп;
  `merge` ждёт чистый индекс основного дерева (`git status --short | grep -v '^??'`).
- Бюджет серии — `limits.budget_usd` (+ `--add-budget`). Лимит итераций по умолчанию в `config.json`.
- Модель ходит через профиль `~/.claude-glm` (Z.AI); `duo selftest` — один дешёвый вызов
  для проверки транспорта.
