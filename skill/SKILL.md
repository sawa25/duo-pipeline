# duo-пайплайн: запуск из любого проекта

Единый источник истины — репозиторий `/home/sawa/GitHub/duo-pipeline/` (код, шпаргалки,
персоны, этот скилл). В проект инструмент НЕ копируется: проект хранит только
`pipeline/<task>/` (артефакты серий) и необязательный `.duo/config.json`.
Подробно: `/home/sawa/GitHub/duo-pipeline/docs/CHEATSHEET-CONTROL.md` (управление) и
`/home/sawa/GitHub/duo-pipeline/docs/PROJECT-SETUP.md` (подключение проекта, ключи конфига).

Команда `duo` доступна из любого каталога; корень проекта определяется сам:
`--repo PATH` > `$DUO_REPO` > git-корень текущего каталога (из `.worktrees/<task>` — основное
дерево). Всегда запускай `duo` из каталога нужного проекта либо передавай корень явно:
`duo --repo /home/sawa/GitHub/<проект> run --task NAME` (`--repo` — глобальный флаг, ставится
ДО подкоманды; после неё argparse его не примет).

## Режимы

| режим | кто | стадии | вызовов модели на итерацию ревью | когда брать |
|---|---|---|---|---|
| `solo` (`--solo`) | один исполнитель на дешёвой `glm-5.3-flash` | только код, без плана и ревью | — | артефактные и измерительные задачи, дорогое планирование избыточно |
| `pair` (`--mode pair`) | исполнитель + один проверяющий (`feynman2` на план, `torvalds2` на код) | план → код | 1 | средний риск: 1–3 файла, чёткие критерии, воспроизводимая проверка |
| `duo` (по умолчанию) | исполнитель + дуэт + председатель | план → код | 7 | схема данных, конвейеры, пре-регистрация, риск тихой подмены результата |

Режим и изоляция пинуются в `state.json` при первом запуске; `--continue`/`--resume`/надзор
берут их оттуда. Ориентиры цены: pair ≈ $5–15 на небольшую серию, duo ≈ $10 за итерацию.

## Подключение проекта (один раз)

```bash
cd /home/sawa/GitHub/<проект>
duo setup            # .duo/config.json, строки в .gitignore, запись в реестр проектов
```

Проект без git: `duo setup` предложит `git init` (нужен хотя бы один коммит для worktree-серий).
В `.duo/config.json` задаются: `executor_env_hint` (окружение/команды тестов для исполнителя),
`executor_worktree_note`, `gates.steps` (гейты поставки в чистой копии), `git.worktree_links`
(какие тяжёлые каталоги линковать в worktree), `guard.never_revert`, `archive.*`.

## Рабочий цикл

```bash
duo init --task NAME --mode pair [--worktree]   # создаёт pipeline/NAME/{task.md,state.json}
                                                # (готовое задание: --task-file ФАЙЛ; режим solo: init без --mode)
# написать задание в pipeline/NAME/task.md (см. «Как писать задание»)
duo run --task NAME                             # стадия «план», detached
duo wait --task NAME --timeout 3600 --quiet     # блокирует до остановки/приёмки: WAIT-RESULT: …
# прочитать plan_vN.md и revNNN_plan.md; если план годится:
duo run --task NAME --continue                  # стадия «код»
duo wait --task NAME --timeout 7200 --quiet
duo gates --task NAME                           # гейты в чистой копии (если настроены gates.steps)
duo commit-by-plan --task NAME --yes            # разложить коммиты по ## commit_plan отчёта
duo merge --task NAME --dry-run && duo merge --task NAME --yes   # только worktree-серии
```

`solo`: `duo init --task NAME`, затем `duo run --task NAME --solo` (план и ревью пропускаются;
итог — `solo_report.md`).
Состояние: `duo status --task NAME` / `duo status --all`; логи — `pipeline/NAME/orchestrator.log`.
Остановки (`needs_human`): `duo run --task NAME --resume [--add-budget USD] [--add-iterations N]`
для машинных halt; решение эксперта — `duo set-verdict --task NAME --verdict ACCEPT|REVISE --note "…"`
или `duo rework --task NAME --phase plan|impl --review FILE --run`.
Все проекты и надзор: `duo projects`; тик надзора `duo supervise` (systemd-таймер по всем проектам).

## Как писать задание (`task.md`)

Задание передаётся исполнителю ЦЕЛИКОМ. Хорошее задание содержит: контекст и цель; **жёсткие
границы записи** (какие пути менять, что не трогать, что не запускать — сеть, прод, перезапуск
сервисов); требования с точными интерфейсами (имена флагов, ключей, форматы); **критерии приёмки
как команды** с ожидаемым выводом (в отчёте исполнитель обязан привести фактический вывод,
а не пересказ); известные подводные камни. Для worktree-серий план обязан кончаться секцией
`## files_touch` (заголовок без номера), отчёт — таблицей `## commit_plan`.

## Правила и грабли

- **Не править `state.json`, `.lock`, `orchestrator*.log`, `transcripts/` руками** — только
  `set-verdict`/`rework`/`run --resume`. Они берут `.lock` и отказывают, пока серия жива.
- **Пока идёт ревью, не создавай новые файлы в репозитории проекта**: оркестратор удаляет всё, что
  сочтёт созданным надсмотрщиком (`ОТКАТ: удалены файлы…`). Свои заготовки — в `/tmp`, переноси после
  вердикта. Для pair/duo в shared-режиме то же относится к правке tracked-файлов.
- **Две серии с кодом в одном дереве запрещены** → параллельные серии только с `--worktree`.
  В worktree попадает только закоммиченное; общие ресурсы вне git (порты, GPU, БД) не изолированы.
- **ACCEPT ≠ гейты воспроизведены**: ревьюер pair не перегоняет тесты, числа в отчёте — со слов
  исполнителя. Сам прогони `duo gates` либо ruff/тесты проекта в чистой копии. Ревью без цитат
  из дифа и без проверенных цифр — «вхолостую», приёмкой не считать.
- Коммит и merge — решение человека: `commit-by-plan --yes` — all-or-nothing, смотри сводку групп;
  `merge` ждёт чистый индекс основного дерева (`git status --short | grep -v '^??'`).
- Бюджет серии — `limits.budget_usd` (+ `--add-budget`). Лимит итераций по умолчанию в `config.json`.
- Модель ходит через профиль `~/.claude-glm` (Z.AI); `duo selftest` — один дешёвый вызов
  для проверки транспорта.
